Ubuntu Server: networking with netplan (static IP, VLAN and bond), SMB and NFS shares in fstab with automount, systemd timers and a server that takes two minutes to boot without mounting the share

A static IP with netplan and netplan try, an LACP bond with a VLAN on top, an SMB share with a credentials file and an NFS one in fstab with _netdev, nofail and x-systemd.automount, a systemd timer versus cron with RequiresMountsFor, and the server that waits two minutes at boot and leaves the share unmounted.

Level 2 · Ubuntu · 9 min read · Updated 6 Nov 2026

What you'll get

An Ubuntu server with its networking written in a file that makes sense, network shares mounted so that a NAS being down doesn't block the boot, and scheduled jobs on systemd timers that leave a log and don't write to the local disk when the share isn't there. And the diagnosis of the typical case after a change window: the server takes two minutes to boot and the NAS folder appears empty.

Before you start

  • Ubuntu Server 24.04 LTS (on 22.04 everything is the same except netplan status), with the basics from the first 30 minutes guide done.
  • Access through the console (vSphere, Proxmox or the iDRAC/iLO one) before touching the network: if you get it wrong over SSH, you are locked out.
  • The network details: IP, mask, gateway, DNS (10.20.30.10 and 10.20.30.11) and search domain contoso.local.
  • A service account in AD for the SMB share (svc-lnx-reports) and the NAS NFS export authorised for the server's IP.

1. Static IP with netplan

The configuration lives in /etc/netplan/*.yaml. A fresh install usually has a 50-cloud-init.yaml; if cloud-init generates it, disable its network handling first or it will overwrite it on the next boot:

  • netplan try applies and, if you don't press Enter within 120 seconds, rolls back. Over SSH it is the only sensible way. netplan apply applies with no safety net.
  • YAML: spaces, never tabs, and indentation matters. sudo netplan generate validates without applying.
  • chmod 600: netplan warns if other users can read the file.
  • optional: true on ens19 (the storage network): boot doesn't wait for that interface to have a link. It is the key to the ticket in section 7.

2. Bond and VLAN

On a physical server with two ports to the same pair of switches: a bond for redundancy and, on top of it, the VLANs that arrive on the trunk.

  • 802.3ad (LACP) needs the port-channel configured on the switches. If you don't control them, mode: active-backup works without touching the switch: one port active and the other on standby.
  • Check the bond with cat /proc/net/bonding/bond0: both ports with MII Status: up and the same Aggregator ID. If each has a different one, the switch isn't doing LACP.
  • Test the redundancy for real: unplug a cable (or shut a port on the switch) with a ping running.

3. A Windows SMB share

The /etc/fstab line:

  • credentials=: the password is never in fstab, which anyone can read. The file is 600 and owned by root.
  • vers=3.1.1: SMB 3 with encryption available; don't let it negotiate SMB1.
  • uid, gid, file_mode, dir_mode: with CIFS the Windows server decides permissions; these values only say who owns the files on Linux. Without uid, everything belongs to root and the application can't write.
  • If the server is joined to the domain with Kerberos (join Linux to AD with SSSD), sec=krb5 avoids storing a password, at the cost of managing the service's ticket.

4. An NFS share

  • Always test by hand before writing fstab. With NFS, permissions go by numeric UID: the reports user must have the UID the NAS expects, or the export has to map it.
  • hard (the default): if the NAS disappears, processes wait instead of getting half-done write errors. It is right for backups; accept that an ls may hang waiting.

5. The three options that prevent a blocked boot

OptionWhat it does
_netdevMarks the mount as a network one: systemd orders it after the network is up. With cifs and nfs4 it infers it from the type, but making it explicit costs nothing
nofailIf the mount fails, boot carries on and the remote file systems target isn't marked as failed
x-systemd.automountDoesn't mount at boot: it creates an automount point and mounts on the first access to the folder. A slow NAS no longer delays boot

After editing fstab:

Two lines: the first is the automount, the second the real NFS. If only autofs shows up, the real mount has failed: look at journalctl -u mnt-backups.mount. The unit name comes from the path (/mnt/backups is mnt-backups.mount).

6. Scheduled jobs: systemd timer or cron

cronsystemd timer
LoggingWhatever you redirect; otherwise local mail nobody readsjournalctl -u service with every run and its code
If the server was offIt doesn't runWith Persistent=true, at boot
DependenciesNoneRequiresMountsFor=, After=, CPU or memory limits
SimplicityOne lineTwo files

For a production job, the timer. A nightly copy of the reports to the NAS:

  • RequiresMountsFor=/mnt/backups: if the NAS can't be mounted, the service doesn't start. Without that line, rsync would write into the empty /mnt/backups folder on the local disk, and the first warning would be a full system disk.
  • RandomizedDelaySec: if twenty servers copy at 01:30, they don't all hit the NAS at once.
  • Start the service by hand once (systemctl start) before leaving it to the timer: that way you see the error calmly.

7. The ticket: "after the reboot it takes two minutes to boot and the NAS folder is empty"

Friday, 8:40. After last night's patching, srv-app-lnx02 (set up before this guide) was slow to come back and the application says it can't find /mnt/backups. On the console, during boot, you could see A start job is running for Wait for Network to be Configured (1min 50s / 2min).

Two problems with the same cause:

  1. The two minutes: systemd-networkd-wait-online waits for all the interfaces it manages to be configured, with a 120-second limit. ens19, the storage network one, is in no-carrier: in last night's window the VM's port group was changed and the network adapter was left disconnected in vSphere.
  2. The share not mounted: the NFS goes through ens19, so the mount fails with Network is unreachable. Because the fstab line had neither nofail nor x-systemd.automount, systemd tried once at boot and never tried again.

What was done:

  • Reconnect the adapter to its port group in vSphere. networkctl moves ens19 to routable.
  • Mount now: sudo mount /mnt/backups and findmnt /mnt/backups.
  • Check whether anything wrote locally: with the share unmounted, the nightly copy wrote to the system disk. sudo umount /mnt/backups && sudo du -sh /mnt/backups showed 38 GB in the local folder; they were deleted and the share mounted again. The service had no RequiresMountsFor.
  • Stop it happening again: optional: true on ens19 in netplan, nofail,x-systemd.automount,x-systemd.mount-timeout=30 in fstab and RequiresMountsFor=/mnt/backups in the backup service. A test reboot comes up in 12 seconds, and with ens19 disconnected on purpose the server still boots and the copy fails with a visible error in the journal instead of filling the disk.

In the ticket: the cause (adapter disconnected during the port group change), the 38 GB recovered and the three configuration changes. And a line for the vSphere network change procedure: check networkctl on the affected VMs after the change.
