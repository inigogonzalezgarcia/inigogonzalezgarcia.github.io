Nagios Core 4.5: hosts, services and templates, NRPE on Linux and NCPA on Windows, notifications and escalations, dependencies, passive checks and a CRITICAL that was not one

Nagios Core 4.5 from source: object configuration (hosts, services, templates, groups and contacts), NRPE on Linux and NCPA on Windows, notifications and escalations, parents and dependencies so one switch does not send twenty emails, nagios -v before reloading, passive checks with freshness, and the check that flips to CRITICAL and back to OK (timeouts, thresholds, SOFT and HARD states).

Level 3 · Nagios: service monitoring · 10 min read · Updated 6 Nov 2026

What you'll get

A tidy Nagios Core: templates that set how things are checked and who gets told, Linux servers watched with NRPE and Windows with NCPA, alerts that move up a level if nobody deals with them, dependencies that turn a switch failure into a single alert, and passive checks for what cannot be queried from outside, such as the nightly backup. And, when the on-call engineer gets a CRITICAL at 2:10 that is OK again by 2:15, knowing whether it is a timeout, a threshold or a badly set max_check_attempts.

Before you start

  • The version: Nagios Core 4.5 (4.5.14 is the latest release at the time of writing). Ubuntu 24.04's nagios4 package is a 4.4, so it is built from source following Nagios's official guide.
  • An Ubuntu Server 24.04 (nagios01, 10.10.99.30) with the baseline from Ubuntu Server: users, SSH, firewall and updates.
  • Ports: 5666/TCP (NRPE) on Linux hosts and 5693/TCP (NCPA) on Windows hosts, open only from nagios01.
  • A mail server that accepts mail from nagios01 and the on-call rota.

1. Install Nagios Core and the plugins

Then the Nagios Plugins (the same project's nagios-plugins package) with ./configure --with-nagios-user=nagios --with-nagios-group=nagios, make and make install: they land in /usr/local/nagios/libexec, the path the $USER1$ variable stands for in commands. And the NRPE client: sudo apt install -y nagios-nrpe-plugin, which puts check_nrpe in /usr/lib/nagios/plugins/.

The web interface is at http://nagios01.contoso.local/nagios. Behind HTTPS if it is used outside the management network.

2. Objects: hosts, services, templates and groups

Everything in Nagios is an object defined in text files. Instead of editing the sample ones, a folder of your own, loaded from /usr/local/nagios/etc/nagios.cfg with cfg_dir=/usr/local/nagios/etc/contoso, and one file per type.

3. NRPE on Linux servers

NRPE is a small service on the monitored server that runs local plugins when Nagios asks. It only runs the commands defined in its configuration:

  • Leave dont_blame_nrpe=0: with arguments from Nagios turned off, whoever reaches port 5666 can only run what you wrote.
  • check_load -r divides the load by the number of CPUs: the same thresholds work for a 2-core server and a 16-core one.

4. NCPA on Windows servers

NCPA is Nagios's cross-platform agent, the one recommended today for Windows. It installs with its MSI or EXE, which asks for a token (the community_string in C:\Program Files\Nagios\NCPA\etc\ncpa.cfg) and listens on 5693/TCP over HTTPS. On Nagios, the check_ncpa.py plugin (from the NCPA repository) in /usr/local/nagios/libexec/:

The token goes in $USER2$, defined in /usr/local/nagios/etc/resource.cfg, which only the nagios user can read: that way it does not show up in object files or on the web interface. On the Windows firewall, an inbound rule for 5693 only from 10.10.99.30.

5. Contacts, notifications and escalations

  • Nagios notifies on reaching a HARD state and repeats every notification_interval minutes (60 in the template) while it stays broken.
  • The escalation kicks in on the third notification (about two hours unresolved with a 60-minute interval) and from then on also notifies responsables-it every 30 minutes. The escalation's group replaces the original one: that is why it includes sistemas again.
  • Acknowledging the problem on the web interface stops the repeats and records who has taken it.
  • For patch windows, Schedule Downtime on the host or group: no alerts during the window and a record that it was planned.

6. Parents and dependencies

If sw-cpd-01 goes down, every server behind it stops answering. With parents sw-cpd-01 on each host (step 2), Nagios marks them UNREACHABLE instead of DOWN, and since the template only notifies on d,r, a single alert arrives: the switch's.

Between services, the same idea with servicedependency: if SQL Server is down, there is no point also alerting about the ERP web app that depends on it.

notification_failure_criteria c,u: while SQL Server is CRITICAL or UNKNOWN, the ERP web app does not notify. The check keeps running (execution_failure_criteria n) so its state is visible on the web interface.

7. Check before reloading: nagios -v

An error in an object file stops Nagios from starting. Always, before reloading:

If there are errors, the output gives file, line and object (a use pointing at a template that does not exist, a misspelt hostgroup_name, an undefined command). With errors, do not reload: Nagios keeps running with the previous configuration.

8. Passive checks

Some things cannot be queried from outside: the nightly backup finishes when it finishes, and it is the backup server that knows whether it went well. With a passive check, the result is sent to Nagios, and freshness alerts if it does not arrive:

The check_dummy command is defined once with command_line $USER1$/check_dummy $ARG1$ "$ARG2$". The result is written to Nagios's external command file. Locally:

From another server it is sent with NRDP (Nagios's HTTP receiver) or NSCA, at the end of the backup script: code 0 if it went well, 2 if it failed. If 26 hours pass with no result, freshness runs check_dummy and the service goes CRITICAL: that way you also find out about the day the script did not even run.

9. The ticket: "Nagios alerts CRITICAL every night and five minutes later it is fine"

For a week the on-call engineer has been getting a Carga (load) CRITICAL on srv-app-01 at 2:10 and a PING CRITICAL on the Valencia branch router; by 2:15, OK. Nobody does anything and on-call starts ignoring the alerts, which is the real problem.

First, what exactly does it say. On the web interface, the service › View Alert History and each alert's status information:

Two different cases:

Load: it is not the load, it is the timeout. The text is not from check_load: it is check_nrpe, which got no reply within 30 seconds. At 2:00 the backup starts and the server is so busy that NRPE is slow to answer. By default check_nrpe turns a timeout into CRITICAL, which is misleading: it does not know the state, it is not that the state is bad.

  • Add -u to the check_nrpe command so a timeout gives UNKNOWN rather than CRITICAL.
  • Check the timeouts fit together: check_nrpe's -t (30) lower than NRPE's command_timeout (60 by default) and than service_check_timeout in nagios.cfg (60 by default).
  • If load during the backup is expected, a check_period that excludes the backup window or a recurring downtime for that service. If it is not expected, the alert was right and the problem is the backup.

PING in Valencia: a threshold too strict and a single attempt. That host has max_check_attempts 1: any failure goes straight to HARD and notifies. A 20% loss is one packet out of five over the VPN with the inter-site backup filling the tunnel.

  • SOFT and HARD: a problem starts as SOFT and Nagios rechecks every retry_interval minutes; only on reaching max_check_attempts does it go HARD and notify. With max_check_attempts 3 and retry_interval 1, a real problem alerts in about 2 minutes and a lost packet never does.
  • Thresholds that suit the link: check_ping -H $HOSTADDRESS$ -w 150.0,20% -c 500.0,60% -p 10. More packets, less weight for a single lost one.

If it also flaps, Nagios marks it with an icon and stops notifying while it lasts. Detection looks at the percentage of state changes over the last 21 checks, compared against low_service_flap_threshold and high_service_flap_threshold in nagios.cfg. Do not turn it off: it means the threshold sits right on the service's normal value, and that is fixed with the threshold.

After the change, nagios -v, reload, and a week of history without false alerts. In the ticket: both alerts, the cause of each, the change to the command or template, and the history afterwards.
