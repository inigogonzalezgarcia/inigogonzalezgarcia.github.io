OPNsense: installation, rules, aliases and groups, Suricata in IDS and then IPS mode, updates and backups, and an alert that blocks legitimate traffic

OPNsense in an office: installation and wizard, aliases and interface groups so rules are not repeated, Suricata first only detecting and then blocking with rulesets and policies, updates and configuration backups, and the accounting firm that cannot upload invoices because the IPS blocks it.

Level 3 · OPNsense: firewall with IDS · 7 min read · Updated 6 Nov 2026

What you'll get

An OPNsense that filters like any firewall and also looks inside the traffic with Suricata: first only alerting, until you know what is normal in the office, and then blocking what is clearly malicious. With rules organised in groups, the configuration saved, and the procedure for when the IPS cuts something the business needs.

Before you start

  • OPNsense 25.7 or later on a box with Intel cards (igb, igc, ix): IPS mode uses netmap and not every card supports it well. For Suricata, at least 8 GB of RAM and a CPU that is not stretched by the office's traffic.
  • The network plan: user VLANs per floor (10.30.20.0/24 and 10.30.21.0/24), servers (10.30.10.0/24), domain contoso.local.
  • The firewall concepts (inbound interface, first matching rule, NAT) are the same as in the pfSense as the office firewall guide; this one covers what changes in OPNsense.

1. Installation and first access

  1. Download the vga (USB) or dvd image from the OPNsense site and check its SHA256 sum.
  2. Boot it: the system starts live. Log in as installer / opnsense to install to disk (choose ZFS). With root / opnsense you try it without installing.
  3. After rebooting, at the console, 1) Assign interfaces and 2) Set interface IP address if the LAN should not be 192.168.1.1/24.
  4. At https://<LAN IP>, root / opnsense, and the wizard: hostname (fw-oficina), domain, DNS, WAN, LAN and the new root password.

Then: a named user under System › Access › Users (in the admins group) and, under System › Settings › Administration, HTTPS, the management interface restricted to the IT network and root SSH access disabled.

2. Aliases, interface groups and rules

Firewall › Aliases supports more types than a basic firewall: Host(s), Network(s), Port(s), URL Table (a list downloaded periodically), GeoIP (by country, with a MaxMind key) and Network group.

Interface groups save you from copying the same rules onto every user VLAN:

The group shows up as one more tab under Firewall › Rules. The evaluation order is Floating, then group, then interface: what all floors share goes on the group and one floor's exception on its interface. Within each tab, the first matching rule wins and whatever matches nothing is blocked.

To find out which rule decided on a connection, Firewall › Log Files › Live View, filtering by the device's IP: each line names the rule and whether it passed or was blocked.

3. Suricata in IDS mode: look first

Before turning anything on, disable offloading on the cards, which stops Suricata from seeing packets as they really are:

Then, Suricata detecting only:

  • Internal interfaces, not the WAN: on the WAN Suricata sees traffic after NAT and every alert points at the firewall itself, not at the device causing it. And whatever arrives from the internet with no rule is already dropped by the firewall.
  • Promiscuous mode is needed if the VLANs hang off the same physical card.
  • Under Download, choose the rulesets: the ET open ones (emerging-malware, emerging-exploit, emerging-phishing, emerging-coinminer, emerging-scan, emerging-policy, emerging-info...) and the abuse.ch ones. Click Download & Update Rules and schedule the daily update with Schedule.

Leave it like that for one or two weeks. Under Alerts you will see what fires and from which devices: whatever is noise (your own scanner, an old office application) is identified now, while nothing is being cut yet.

4. Policies and the move to IPS

Policies (the Policy tab) change the action of many rules at once without touching rules one by one. Each policy says: from these rulesets, rules with this action move to that other one.

  • Only block high-confidence categories. emerging-policy and emerging-info describe behaviours (a file sharing service, a domain under an unusual TLD) that are often legitimate in an office: they stay on Alert.
  • If two policies affect the same rule, the one with the lowest priority number wins.

With the policies in place, under Settings tick IPS mode (in recent versions, Capture mode: Netmap (IPS)) and apply. The interfaces reset for a moment: do it out of hours. Under Alerts, the Action column now shows blocked for what is dropped.

If the card does not get on with netmap (drops, very poor throughput), the dev.netmap.admode=2 tunable under System › Settings › Tunables forces emulated mode. It is slower, but stable.

5. Updates and backups

  • System › Firmware › Status › Check for updates. Minor updates come out every few weeks; major versions (25.7, 26.1...) twice a year, applied from the same page after reading the notes. If they bring a new kernel, they ask for a reboot.
  • From the console, option 12) Update from console does the same if the web UI does not respond.
  • System › Configuration › Backups › Download configuration, encrypted with a password. Before every update and after every important change.
  • System › Configuration › History keeps every change with who made it: compare two versions and revert to an earlier one.
  • With ZFS, System › Snapshots creates a boot point before updating: if the new version fails, boot from the previous one.

6. The ticket: "the accounting firm can't upload our invoices since the IPS went in"

Wednesday, 9:15. Accounts cannot download or upload files on the accounting firm's exchange portal: the browser keeps loading and ends with connection reset. From a phone on mobile data, it works.

  1. Is it the IPS? Under Alerts, filtering by the accounts workstation's IP:
  1. Why is something from emerging-info being blocked? Under Policy there is a second policy, added last week "to be on the safe side", that moves all of emerging-info and emerging-policy to Drop. That is the underlying mistake.
  2. The three tools, from most general to most specific:
  • Fix the policy: remove emerging-info and emerging-policy from the blocking policy. It is the real fix: those rulesets describe behaviours, not threats.
  • An exception for one rule: a policy with priority 1, SID 2059421 (or filtering by ruleset and rule) and New action: Alert. It keeps alerting, it no longer blocks. A manual change on the Rules tab does the same for a single rule and is marked as __manual__.
  • A pass list under User defined: a rule with Destination IP 203.0.113.80 and Action: Pass, so Suricata stops inspecting that traffic. Only for known, stable destinations, with a description and a review date: an overly broad pass is a hole.
  1. Check: accounts uploads a test invoice; under Alerts the entry shows as allowed (if it stayed as an alert) or does not appear (if it goes through the pass list).

In the ticket: the alert and SID, the policy that turned it into a block, the change applied and who approved it. And, in the firewall's change log, the golden rule: no new Drop policy without a week on Alert first.
