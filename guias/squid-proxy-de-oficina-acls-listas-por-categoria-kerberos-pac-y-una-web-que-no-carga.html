Squid: office proxy with ACLs, category block lists, Kerberos with Active Directory, PAC and a supplier website that will not load

Squid 6 on Ubuntu as the office proxy: the port, ACLs and why order decides everything, category blocks from files, Kerberos authentication with Active Directory and groups, why SSL bump rarely pays off, PAC and WPAD, reading access.log, and a supplier website that will not load through the proxy.

Level 3 · Squid: the office web proxy · 9 min read · Updated 6 Nov 2026

Rather practise it?Solve the simulated ticket "The proxy blocks a supplier's website" in SysAdmin Desks ↗

What you'll get

A web proxy for the office that knows who is browsing (with their Active Directory user, without asking for a password), applies different rules per group, blocks categories from lists kept in files and leaves a readable record of every connection. And, when a website "will not load through the proxy", finding in one access.log line whether it is a rule, a port, authentication or the way out to the Internet.

Before you start

  • An Ubuntu Server 24.04 with the baseline from Ubuntu Server: users, SSH, firewall and updates. The squid package in Ubuntu 24.04 is version 6.
  • A DNS name, proxy.contoso.local, pointing at the server (10.10.99.40). Kerberos needs it: it does not work with the IP.
  • Time synchronised with the domain controllers and a service account in AD, svc-squid, with a non-expiring password.
  • On the perimeter firewall, outbound 80 and 443 only from the proxy (if desktops can also go out directly, the proxy is optional and nobody notices).

1. Install, and where the configuration goes

Ubuntu's squid.conf is long and commented; yours goes in a separate file, /etc/squid/conf.d/contoso.conf, loaded at the include: after the port safety rules and before the final deny all. The default port, 3128, is already defined; do not repeat it in your file or Squid will try to open it twice.

Two commands for every change:

-k parse checks the syntax without touching the service; -k reconfigure reloads without dropping open connections.

2. ACLs: order decides everything

An ACL is a named condition (source, destination, port, user, group). http_access rules are evaluated top to bottom and the first one whose conditions all match wins (conditions on the same line are ANDed). If none matches, the opposite of the last one applies, which is why everything ends in http_access deny all.

The practical consequences:

  • Exceptions go before blocks. An allow list below a deny never gets read.
  • Whatever must not ask for authentication (Windows updates, antivirus, services that cannot authenticate) goes before the rule that requires a user.
  • http_access deny !autenticado is the usual way to force authentication: when it fails, Squid answers 407 and the browser authenticates.

3. Category lists in files

One list per category in /etc/squid/listas/, one domain per line. The leading dot includes subdomains:

And the rules in conf.d, in this order:

  • With HTTPS the proxy only sees the name (the CONNECT host:443 request), not the full URL. That is enough to block by domain, and dstdomain works the same for HTTP and HTTPS.
  • squid -k parse warns when a domain appears twice or is already covered by another (.example.com and www.example.com). Clean up those warnings: in big lists they hide real errors.
  • Lists can be downloaded from a category provider and refreshed by a nightly script ending in squid -k reconfigure. Keep the previous version to roll back if an update blocks something important.
  • The exceptions list is decided by someone with authority (not whoever is on shift), and each entry has a ticket.

4. Kerberos authentication with Active Directory

With Kerberos (Negotiate), the browser presents the Windows session's ticket and the user sees no prompt. You need a keytab with the HTTP/proxy.contoso.local principal. On a domain controller:

Copy it to /etc/squid/HTTP.keytab (owner proxy, mode 400) and delete the copy on the DC. On the proxy:

The KRB5_KTNAME variable is used by the group helper; the authentication helper gets the keytab with -k. At the top of contoso.conf:

  • -r strips the realm from the name: the log shows laura.prado, not laura.prado@CONTOSO.LOCAL.
  • The group helper queries AD over LDAP with the keytab's identity and caches the answer for an hour (ttl=3600): a user added to the group may take up to an hour to notice, or until a squid -k reconfigure.
  • NTLM as a fallback (devices outside the domain) means joining the proxy with Samba winbind and negotiate_wrapper_auth. If every desktop is in the domain, better not: it is one more piece to maintain.

Kerberos only works if the browser reaches the proxy by name. If the PAC or the GPO says 10.10.99.40:3128, the browser finds no ticket for that IP, tries NTLM and, with no NTLM configured, the user gets a credentials prompt that accepts nothing.

5. SSL bump: why hardly ever

SSL bump decrypts HTTPS at the proxy: Squid creates on the fly a certificate for each website signed by an internal CA that every device must trust. It shows full URLs and allows content inspection, but:

  • It breaks applications with certificate pinning: banking clients, updaters, some desktop and mobile apps. Each one ends up on the exception list.
  • The internal CA becomes critical: whoever holds its key can impersonate any website to any device.
  • Decrypting employees' banking, health or personal email has legal and privacy implications decided with HR and the DPO, not in a config file.
  • It needs the squid-openssl package and more CPU.

Blocking by domain does not need it: with an explicit proxy the name already travels in the CONNECT. If the requirement is content inspection, it is usually better solved on the perimeter firewall or by a dedicated web security service.

6. Distributing the settings: PAC and WPAD

A PAC is a small JavaScript file the browser consults for every URL, deciding between proxy and direct:

  • It is served over HTTP from any internal web server with MIME type application/x-ns-proxy-autoconfig.
  • It is distributed as the script URL: by GPO (Internet Settings preferences), with Edge's ProxyPacUrl policy, or in Intune from the settings catalog. Edge and Chrome use the system settings unless they have their own.
  • WPAD is automatic discovery (http://wpad.contoso.local/wpad.dat). It works, but Windows DNS Server blocks the name wpad by default (global query block list), and opening it lets a malicious device announce itself as the proxy. An explicit URL by policy is more predictable.
  • "PROXY proxy.contoso.local:3128; DIRECT" goes direct if the proxy is down. That only makes sense if the firewall allows direct egress; otherwise the user just gets a different error.

7. Reading access.log

/var/log/squid/access.log, one line per request. Times are in seconds since 1970; to read them:

Columns: time, milliseconds, client IP, result/code, bytes, method, destination, user, how it went out, and type.

ResultWhat it means
TCP_TUNNEL/200HTTPS allowed: tunnel open
TCP_MISS/200HTTP served from the origin
TCP_DENIED/407 with user -Squid asks for authentication. Normal once before the good one; in a loop, the client cannot authenticate
TCP_DENIED/403An http_access deny rule blocked it
.../503 with HIER_NONESquid could not resolve or connect to the destination

8. The ticket: "the supplier's website will not load through the proxy"

Purchasing cannot get into a supplier's portal, https://portal.fabrikam.com:8443. Edge shows ERR_TUNNEL_CONNECTION_FAILED; from a phone on mobile data, it loads. That error is the browser's when the proxy answers the CONNECT with something other than 200: the answer is in the log.

A 403 with the user identified: it is not authentication, it is a rule. In order:

  1. Is it on a list? grep -rn fabrikam /etc/squid/listas/ returns nothing.
  2. The port? The first rules in squid.conf deny CONNECT to ports not in SSL_ports, and on Ubuntu that ACL only holds 443. That is the 403.
  3. The fix, in /etc/squid/squid.conf next to the acl SSL_ports port 443 line: acl SSL_ports port 8443. If you would rather not open 8443 to every destination, a dstdomain ACL for the supplier and a combined http_access allow CONNECT rule placed before the deny CONNECT !SSL_ports.
  4. sudo squid -k parse && sudo squid -k reconfigure and test again:
  1. Now a 503 after 30 seconds: the rule lets it through, but the proxy cannot connect. The perimeter firewall only lets the proxy out on 80 and 443. Request the outbound rule to 8443 towards the supplier's IP (with its ticket) and the test returns 200.

Other endings for the same symptom: TCP_DENIED/407 in a loop with user - (an app that cannot authenticate: its domain goes in sin-autenticacion.txt); a 403 from a list that includes the supplier's CDN (a documented exception); an immediate 503 from DNS (the proxy resolves with its own DNS servers: dig portal.fabrikam.com from the proxy).

In the ticket: log line before and after, the rule or ACL changed, the firewall change if any, and the final test.
