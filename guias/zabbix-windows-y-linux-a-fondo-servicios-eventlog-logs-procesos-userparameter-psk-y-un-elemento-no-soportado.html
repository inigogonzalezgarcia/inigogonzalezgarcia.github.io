Zabbix: Windows and Linux in depth with agent 2, with discovered services, event log, log files, processes, UserParameter, PSK encryption and a "not supported" item

Beyond the template: which Windows services and systemd units to watch with macros, Windows events with eventlog[], application logs with log[] and logrt[], processes with proc.num, your own scripts as UserParameter, PSK encryption between server and agent, and what to do when an item goes not supported.

Level 3 · Zabbix: server, agents and templates · 9 min read · Updated 6 Nov 2026

What you'll get

Zabbix knowing as much about the servers as the team that runs them: which services must be running, which Windows events matter, which errors the application writes to its log, how many processes there should be and how many hours old the last backup is. All with agent 2, encrypted with PSK, and knowing how to read the reason when an item is stuck in Not supported.

Before you start

  • Zabbix 7.0 LTS with agent 2 rolled out as in the server, agent 2 and templates guide, and the Windows by Zabbix agent and Linux by Zabbix agent templates linked.
  • Active checks working: event log and log file items only exist in active mode. ServerActive points to the server (or proxy) and Hostname matches the host name in Zabbix.
  • Administrator access to the servers to edit the agent configuration and restart the service.
  • The list of what is critical on each server, asked of the application owner: services, log paths, processes and the backup path.

1. Services: Windows and systemd

The Windows template discovers services with automatic startup and alerts on those that are stopped. What goes into discovery is decided with macros, on the host or on a template of your own per server type:

  • Without touching {$SERVICE.NAME.MATCHES}, every automatic service is watched except the template's exclusion list. On application servers a closed list is better: only the services that stop the business.
  • A service on Automatic (Delayed Start) that is slow to start after a reboot gives a false alert for a few minutes: the template trigger looks at several values in a row, and a maintenance period covers patch windows.
  • The item is service.info["ErpAppSvc",state]: 0 is running, 6 stopped and 255 means the service does not exist.

On Linux, agent 2 ships the systemd plugin. Link the Systemd by Zabbix agent 2 template and filter the same way:

2. The Windows event log with eventlog[]

eventlog[name,<regexp>,<severity>,<source>,<eventid>,<maxlines>,<mode>] reads an event log and sends the entries that pass the filter. Type Zabbix agent (active), type of information Log:

What to watchKeyWhere
A service that crashes`eventlog[System,,,"Service Control Manager","^(70317034)$",,skip]`Every Windows server
Unexpected rebooteventlog[System,,,"Microsoft-Windows-Kernel-Power","^41$",,skip]Every Windows server
Locked-out accounteventlog[Security,,,,"^4740$",,skip]Domain controller holding the PDC role
Disk I/O errors`eventlog[System,,"WarningError",,"^(129153)$",,skip]`Physical servers and VMs
  • skip makes the agent start from the end of the log the first time: without it, it sends the whole log history at once.
  • The Security log needs the agent to run as Local System (the MSI default) and auditing to be enabled by GPO; with no auditing there is no 4740 event to read.
  • Filter on the agent (id, source, severity), not in the trigger: that way thousands of events do not travel to the server to be thrown away there.

A trigger on a log item closes manually or when no more data arrives. For the crashing service:

The event text reaches the alert through {ITEM.VALUE}: whoever gets the email sees which service went down without logging on to the server.

3. Log files on Linux with log[] and logrt[]

  • log[file,<regexp>,<encoding>,<maxlines>,<mode>,<output>] follows a fixed file.
  • logrt[file_regexp,<regexp>,...] follows rotating files; the regular expression is only allowed in the file name, not in the path.

The agent runs as the zabbix user and must be able to read the file. nginx logs belong to www-data:adm:

  • maxlines (100 in the example) limits the lines per second the agent sends: an error loop does not flood the database.
  • With many expected errors, counting is better than sending: log.count[...] and logrt.count[...] return the number of matching lines, a number you can graph and compare with a threshold.

4. Processes with proc.num

proc.num counts processes. On Windows it takes a name and a user; on Linux, also a state and the command line:

  • On Linux the name is the executable's (java, not the service's). To tell two Java applications apart on the same server, the fourth parameter filters on the command line.
  • Typical triggers: last(/srv-app-02/proc.num[java,tomcat,,org.apache.catalina.startup.Bootstrap])=0 (the application is not running) and a maximum for processes that multiply, such as PHP-FPM workers.

5. Your own scripts with UserParameter

What no template knows (the age of the ERP backup, the days left on a certificate) becomes an item through a UserParameter: a new key that runs a command and returns a value.

Windows, in a file of your own inside the agent folder. If zabbix_agent2.conf has no Include line pointing to that folder, add one:

Linux, with parameters ([*] and $1) to reuse the same script:

  • The script always returns a number, also when it fails (the 9999 on Windows): an error text in a numeric item leaves it not supported.
  • It runs under the agent's account: Local System on Windows (with no mapped network drives) and zabbix on Linux (with no sudo).
  • Backslashes, quotes, *, $, |, ;, & or brackets in parameters are forbidden unless UnsafeUserParameters=1. Better not to enable it and pass simple parameters.
  • The item in Zabbix: type Zabbix agent, key contoso.backup.age_hours, numeric, and a trigger last(/SRV-ERP-01/contoso.backup.age_hours)>26.

6. PSK encryption between server and agent

Without encryption, the conversation between server and agent travels in clear text and anyone reaching 10050 can impersonate the server if they are in the Server list. With PSK, a shared key per host:

On Windows, the MSI takes the same at install time: TLSCONNECT=psk TLSACCEPT=psk TLSPSKIDENTITY=PSK-SRV-ERP-01 TLSPSKVALUE=<key>, and writes the key to a file next to the configuration.

On the host, Encryption tab:

  • One key and identity per host: if one leaks, only that server is affected. The identity is not secret; the key is, and the interface never shows it again.
  • To move from clear text to PSK without gaps: first in Zabbix Connections from host with both No encryption and PSK ticked, then the agent, and finally untick No encryption.
  • The test from the server: zabbix_get -s 10.10.30.21 -k agent.ping --tls-connect psk --tls-psk-identity PSK-SRV-APP-02 --tls-psk-file /root/psk-srv-app-02.psk.

7. The ticket: "the ERP backup item shows Not supported"

Tuesday, 8:50. The old-ERP-backup trigger has never fired, and someone asks whether it works. In Monitoring › Latest data, the contoso.backup.age_hours item on SRV-ERP-01 has no value and shows Not supported. The information icon next to it gives the reason, and each reason has its fix:

  1. Unsupported item key: the agent does not know the key. The contoso.conf file is not included in the configuration, the key name has a typo, or the agent service has not been restarted since it was created. Test on the server itself, with the full configuration path:
  1. Timeout while executing a shell script: PowerShell is slow to start and the script takes longer than the default 3 seconds. In Zabbix 7.0 the timeout is set per item (the item's Timeout field, for example 15s) or for every agent item in Administration › General › Timeouts. Do not raise the global value for a single script.
  2. Value of type "string": the script returned an error instead of a number. Here, the Z:\ERP path is a mapped drive that exists in the administrator's session but not for Local System. It is replaced with the local or UNC path, and the script returns 9999 if it finds nothing.
  3. Check again: Zabbix retries unsupported items every 10 minutes (Administration › General › Other › Refresh unsupported items). To avoid waiting, Execute now on the item. Latest data shows 7 and the trigger can now fire.
  4. So it never fails silently again: an internal action in Alerts › Actions › Internal actions with the condition Event type equals Item in "not supported" state and the production host group, notifying the monitoring team (not on-call). A broken item is not an outage, but a trigger that can never fire is worse.

In the ticket: the exact not supported message, the -t test on the server, the cause and a screenshot of Latest data with the value.
