Active Directory: domain time, the PDC emulator with external NTP, the GPO only where needed, virtual DCs and a computer six minutes off

A domain's time hierarchy (PDC emulator, domain controllers, members), the PDC against external NTP with w32tm, a GPO with a WMI filter for the PDC only, virtual DCs and host time sync, w32tm /query /status, /monitor and /stripchart, and the Kerberos KRB_AP_ERR_SKEW error from a computer six minutes off.

Level 2 · Active Directory: delegation and auditing · 8 min read · Updated 6 Nov 2026

What you'll get

Every computer in the domain with the same time, taken from a reliable source along a single path: the PDC emulator against external NTP, the other domain controllers against it and the members against the domain controllers. And knowing how to solve the ticket that arrives when a computer drifts more than five minutes: Kerberos stops working and the user cannot sign in or open anything.

Before you start

  • Domain admin, or permission to edit GPOs linked to the Domain Controllers OU.
  • Knowing which domain controller holds the PDC emulator role: (Get-ADDomain).PDCEmulator or netdom query fsmo.
  • Outbound UDP 123 from the PDC, and only from the PDC, to the chosen NTP servers (or an internal NTP source on the network, if there is one).
  • If the domain controllers are virtual machines, access to the VM settings in Hyper-V or vCenter.

1. The time hierarchy

ComputerWhere it takes the time fromType (w32tm /query /configuration)
PDC emulator of the forest root domainExternal NTP servers or an internal NTPNTP
Other domain controllers in the domainThe PDC emulator (or another DC in its hierarchy)NT5DS
Member servers and workstationsThe domain controller that authenticates themNT5DS
  • NT5DS means "follow the domain hierarchy" and is what every domain-joined computer has by default. Nothing needs configuring on them.
  • The one piece you do configure is the PDC. Without an external source it uses its own clock, and the error spreads to the whole domain. The time service warns about it with Time-Service event 12 in the PDC's System log.
  • Kerberos tolerates 5 minutes of difference between client and domain controller by default (Kerberos Policy › Maximum tolerance for computer clock synchronization). You do not raise it: you fix the time.

2. The PDC against external NTP

On the PDC emulator, in an elevated command prompt:

  • 0x8 requests normal NTP client mode; several servers separated by spaces, in quotes.
  • /reliable:yes advertises the PDC as a reliable time source to the rest of the domain.
  • Local CMOS Clock or Free-running System Clock as the source on a PDC is exactly what needs fixing.

If the PDC role moves to another domain controller (maintenance, replacement), the configuration does not travel with it. On the old one: w32tm /config /syncfromflags:domhier /reliable:no /update and restart the service; on the new one, the commands above. The GPO in section 3 does this by itself.

3. A GPO for the PDC only

With a GPO, the configuration follows the role even when it changes server. The key is that only the PDC receives it: a WMI filter that keeps the domain controller whose DomainRole is 5.

  1. In GPMC, WMI Filters › New: name DC-Emulador-PDC, namespace root\CIMv2, query Select * from Win32_ComputerSystem where DomainRole = 5.
  2. A new GPO DC-Hora-PDC, linked to the Domain Controllers OU, with the WMI filter above.
  3. In the GPO:

AnnounceFlags 5 means "time server and reliable source", the same as /reliable:yes.

What you do not do: an NTP client GPO linked to the whole domain. It sends every workstation to ask the internet, breaks the hierarchy and causes a lot of drift. If an old one exists, gpresult /scope computer /h report.html on a workstation shows it under Windows Time Service. Computers outside the domain (joined only to Entra ID, for example) use time.windows.com by default and need nothing.

4. Virtual domain controllers and host time

A virtual DC has two possible sources: the domain hierarchy and the hypervisor. If both correct the clock at once, the time jumps, and if the host is wrong, the DC follows it.

  • Hyper-V: Microsoft's recommendation is to leave the Time Synchronization integration service on (it corrects the clock when the VM starts or is restored) and turn off, inside the DC, the provider that syncs continuously:

On the PDC the source must be the NTP from section 2, and on the others another DC; if it shows VM IC Time Synchronization Provider, the change has not taken effect.

  • VMware: on the VM, Edit Settings › VM Options › VMware Tools, untick Synchronize time with host. Even so, VMware Tools corrects the time on some events (Tools startup, resume, snapshot restore, vMotion). To stop it completely, the VM advanced parameters documented by VMware, such as time.synchronize.tools.startup, time.synchronize.resume.disk and time.synchronize.restore set to 0.
  • In both cases the host must have NTP configured correctly: for ESXi, see the guide on installing an ESXi 8 host.

Do not restore a DC from an old snapshot to "fix" something: besides the time, it can break replication. The AD Recycle Bin is there for that.

5. Checking: status, monitor and stripchart

  • Source: a DC on a member, another DC or the NTP on a DC, the external NTP on the PDC. If a member shows Local CMOS Clock or time.windows.com, someone has configured it by hand.
  • Last Successful Sync Time: if it is days old, the computer cannot reach its source (UDP 123 blocked between sites, for example).
  • /stripchart measures the difference with another computer right now: the column is how far ahead (+) or behind (−) the other one is compared to you.

To see every domain controller at once, w32tm /monitor /domain:contoso.local: each DC with its source and its offset from the PDC. The warning events, in the System log, source Time-Service: 12 (the PDC has no reliable source), 36 (not synchronized for 24 hours), 37 (receiving valid time from its source) and 47 (a configured NTP server does not respond).

6. The ticket: "I can't open the drive or the intranet, and at sign-in it says something about the time"

Thursday, 9:20. An Accounting workstation, PC-0219. The user says it worked yesterday. This morning, signing in with the network connected, Windows says There is a time and/or date difference between the client and server. In a session that was already open, the network drives give access denied.

  1. The offset: the taskbar clock says 9:26; yours, 9:20. From your computer, w32tm /stripchart /computer:PC-0219 /samples:3 /dataonly gives about +360 seconds: six minutes, more than the five Kerberos tolerates.
  2. The error on the DC: in the domain controllers' Security log, events 4771 for that account with failure code 0x25, which is KRB_AP_ERR_SKEW: the client's timestamp is outside the window.
  3. Why it drifted. On the device, as local administrator (the LAPS account if the domain will not let you in):

(Local) means someone changed it on the computer itself (a vendor tool, a technician, an image prepared outside the domain). Outbound UDP 123 is closed for workstations, so it has not synced for weeks and the clock has drifted. If it said (Policy) instead, a GPO would be to blame.

  1. The fix: back to the hierarchy, sync and renew the tickets.

If the offset is so large the computer cannot sync, set the time by hand (Set-Date) and repeat the /resync.

  1. Making sure it does not happen again: if more computers show the same problem, w32tm /monitor against the DCs rules out the whole domain; if the PDC is wrong, everything is wrong at once and section 2 is the fix. For a single computer, the model or image record: remove the manual NTP configuration before deploying it.

In the ticket: measured offset, event 4771 with 0x25, source found (time.windows.com configured locally), the commands and the check: source is a DC and the user opens the drive.
