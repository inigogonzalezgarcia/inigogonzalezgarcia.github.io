Splunk Enterprise: forwarders, indexes, SPL searches, a dashboard, an alert, the licence and a source that stops arriving

The parts of Splunk Enterprise (universal forwarder, indexer, search head and deployment server), inputs.conf and outputs.conf, indexes with retention, the Windows and Linux add-ons, the SPL operations uses every day, a dashboard and a scheduled alert, licence volume, and diagnosing a server whose logs stop arriving.

Level 4 · Splunk: logs, searches and alerts · 11 min read · Updated 6 Nov 2026

What you'll get

Running a Splunk Enterprise that already exists or is being set up for IT: knowing where each log comes in, which index it ends up in and how long it is kept, writing the searches that come back every week, leaving a dashboard and an alert that warn without anyone watching, keeping an eye on the licence and finding out why a server has stopped sending data.

Before you start

  • Splunk Enterprise 9.4 or 10.x with an administrative role (admin, or your own with edit_monitor, edit_indexes and list_deployment_server).
  • Access to the deployment server and to the command line of one forwarder of each kind (Windows and Linux).
  • The default ports: 8000 (Splunk Web), 8089 (management and deployment server), 9997 (receiving on the indexers, by convention) and 8088 (HTTP Event Collector).
  • If the company uses Microsoft Sentinel for security, the Microsoft Sentinel guide explains the cloud equivalent; this one stays in Splunk.

1. The parts and how an event travels

PartWhat it doesWhere
Universal forwarder (UF)Reads files and event logs and sends them, without indexingOn every server
IndexerReceives on 9997, breaks events, assigns the timestamp and writes to the indexsplunk-idx01/02.contoso.local
Search headWhere you search, build dashboards and schedule alertssplunk.contoso.local:8000
Deployment serverHands configuration apps out to the forwarderssplunk-ds.contoso.local:8089

The path is always the same: the UF reads according to its inputs.conf, sends according to its outputs.conf, the indexer applies props.conf and transforms.conf (time zone, date format, line breaking) and writes to the index. Almost every problem is explained by finding which leg the event is lost on.

On the forwarder, configuration lives in C:\Program Files\SplunkUniversalForwarder\etc\ (Windows) or /opt/splunkforwarder/etc/ (Linux). Since 9.1, the Linux UF installs with the unprivileged user splunkfwd: whatever it has to read must be readable by that user.

2. inputs.conf and outputs.conf

Nobody edits forwarders one by one: configuration goes into small apps that the deployment server hands out from $SPLUNK_HOME/etc/deployment-apps/.

With two indexers in server, the forwarder load-balances between them and switches every 30 seconds (autoLBFrequency). useACK means it does not count a block as sent until the indexer confirms it.

The rules that save trouble:

  • Always index =. Without it, everything ends up in main, with the default retention and where nobody looks for it.
  • Always sourcetype = with the name the add-on expects, so fields are extracted automatically.
  • outputs.conf in one app and inputs in another: a change of indexers then does not touch the inputs.

On the deployment server, Settings › Agent management (Forwarder management before version 10) ties apps to server classes: for example, the linux-servers class with the filter *lnx* gets contoso_all_outputs and contoso_linux_inputs, with Restart Agent ticked. One indexer showing as inactive at that moment is normal: the forwarder uses one at a time. If both are inactive, nothing is being sent.

3. Indexes, retention and the add-ons

One index per data type and per audience: wineventlog, linux, web, network, firewall. Search permissions are granted per index on the role, so separating them is what keeps the web team out of the security log.

  • frozenTimePeriodInSecs: the age at which data is deleted (or archived, if coldToFrozenDir is set). 31,536,000 seconds is 365 days; the default is about 6 years.
  • maxTotalDataSizeMB: the size cap; whichever is reached first wins. If the disk fills before the planned age, history is lost without warning: size with both.
  • Indexes are created identically on every indexer; if a forwarder sends to an index that does not exist, the events are dropped and the indexer notes it in splunkd.log.

The two add-ons everybody installs, from Splunkbase:

  • Splunk Add-on for Microsoft Windows (Splunk_TA_windows): ships the event log inputs disabled. Enable them in your own local/inputs.conf, for example [WinEventLog://Security] with index = wineventlog, renderXml = true (events arrive with the XmlWinEventLog sourcetype) and disabled = 0.
  • Splunk Add-on for Unix and Linux (Splunk_TA_nix): log files and CPU, memory and disk scripts, also disabled by default. Enable only what you will use: every script that runs each minute costs licence.

Add-ons are installed on the forwarder (inputs) and on the search head and indexers (field extraction). If they are only on the forwarder, the data arrives but the fields do not appear.

5. A dashboard and a scheduled alert

The dashboard. In Search & Reporting › Dashboards › Create New Dashboard, with Dashboard Studio, an "IT Operations" dashboard with four visualisations, each with its own search: the tstats search above as a table, 4625s per hour as a line chart, top errors per server as bars and licence usage from section 6. A global Time range input with Last 24 hours by default.

The alert. From the servers-with-no-data search, Save As › Alert:

  • Throttle on host: one alert per server every four hours, not one every 15 minutes.
  • An alert's search should finish in seconds. If it is slow, use tstats or a specific index instead of index=*.
  • Scheduled alerts run as their owner: if that person leaves and their user is deleted, the alert is orphaned. Reassign them to a service account in Settings › Searches, reports, and alerts.

6. Licence volume

The Splunk Enterprise licence measures what is indexed per day (midnight to midnight on the license manager's clock), not what is stored. Going over on a given day raises a warning; with a licence under 100 GB/day, 45 warnings in 60 days block search (alerts included) until you get a reset licence. Above 100 GB/day there are warnings but no block. Indexing never stops.

In license_usage.log, b is bytes, idx the index, st the sourcetype and h the host. Swap by idx for by st or by h to find who has grown. The usual culprits: a server with debug logging on, a firewall logging all allowed traffic or a Linux add-on script running every 10 seconds. Settings › Licensing › Usage report shows the same with charts.

An alert when the day reaches 80% of the licence gives time to react before midnight.

7. The ticket: "since Tuesday web03's logs don't show up in Splunk"

Thursday, 9:00. The web team searches for last night's error in index=web host=web03 and there is nothing since Tuesday at 22:00. The alert from section 5 had already flagged it.

  1. Not arriving, or arriving with the wrong time? Search by when it was indexed, not by the event date:

If there were events with lag_min near -60 or +60, the problem would be the time zone: the server has changed zone or the date format does not include it, and events are stored an hour off. That is fixed in the indexer's props.conf with TZ = Europe/Madrid in the sourcetype stanza (or [host::web03]), and dates are checked in index=_internal component=DateParserVerbose. Here nothing arrives at all: carry on.

  1. Is the forwarder talking to Splunk? The UF's internal logs reach the _internal index by the same path:
  • If _internal has nothing from web03 either, the forwarder is not getting through: on the server, systemctl status SplunkForwarder, splunk list forward-server, nc -vz 10.20.0.11 9997 and /opt/splunkforwarder/var/log/splunk/splunkd.log looking for TcpOutputProc. A full disk on the forwarder, a firewall change or an expired TLS certificate between forwarder and indexer are the usual causes.
  • Here the forwarder is talking, but cannot read the file.
  1. The cause: on Tuesday at 22:00 a new Nginx version was deployed and the package left /var/log/nginx/ with 0750 www-data:adm. The splunkfwd user is not in that group.

The default ACL (-d) makes new files created by logrotate readable too. Adding splunkfwd to the adm group also works, but grants more than needed.

  1. Do the two days come back? The forwarder remembers how far it read each file (the fishbucket), so it reads what is missing as soon as it has permission, provided logrotate has not deleted the rotated files. Check with index=web host=web03 earliest=-3d | timechart span=1h count that the gap fills in.

In the ticket: symptom, the leg where it was lost (reading on the forwarder), cause (permissions after the Nginx upgrade), change (ACL for splunkfwd), data recovery and the task so the Nginx deployment includes the ACL.
