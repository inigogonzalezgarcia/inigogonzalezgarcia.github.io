PowerChute Network Shutdown on VMware and Windows: the virtual appliance, pairing with the UPS card, the shutdown sequence, delays and thresholds, a controlled test and hosts that shut down before the VMs

PowerChute Network Shutdown with vCenter: deploying the virtual appliance, pairing it with the Network Management Card, the shutdown order of VMs, vCenter, hosts and storage, the timing maths with runtime and Low Battery Duration, PowerChute on a physical Windows server, a test with a real power cut, and the case of hosts that went down with VMs still running.

Sector 5 · UPS - Powering the comms room · 9 min read · Updated 6 Nov 2026

What you'll get

If the outage lasts longer than the battery, the vSphere cluster and the physical servers shut themselves down in order: first the VMs with a clean shutdown, then vCenter, then the hosts and finally everything else, all before the UPS runs out. And proving it with a real test, not with faith in a configuration screen. The APC UPS network card guide gets the card ready and introduces PowerChute; this one goes into the detail of the sequence.

Before you start

  • The UPS Network Management Card 3 configured: static IP, time by NTP, alerts and the PowerChute authentication phrase (UPS › Configuration › PowerChute).
  • The measured runtime with the real load (from the last annual test, as in the comms room UPS guide), not the catalogue figure.
  • In vCenter, an account for PowerChute with the administrator role (svc-pcns@vsphere.local or an AD one) and the list of VMs with their priority, agreed with the application owners.
  • VMware Tools running in every VM: without it, PowerChute can't request a clean shutdown and powers it off hard.
  • Open between PowerChute and the card: TCP 80 or 443, 3052 and 6547 and UDP 3052.

1. The PowerChute virtual appliance

On vSphere, PowerChute Network Shutdown (version 5.x) is installed as a virtual appliance: an OVA file deployed with Deploy OVF Template.

  • A static IP on the management network, the same one from which the card and vCenter are reachable, with its name in DNS (pcns01.mgmt.contoso.local).
  • Where to put it: on a cluster host, with no automatic vMotion moving it around uncontrolled (a DRS rule pinning it to a host, or DRS set to manual for that VM). PowerChute shuts itself down near the end, with vCenter, and needs to know which host it is on.
  • The web console is at https://pcns01.mgmt.contoso.local:6547. The first-run wizard asks, in order: the environment type (vCenter), the vCenter and its account, the hosts it protects, whether vCenter is a VM inside those hosts, and the UPS card.

If vCenter runs inside the protected cluster, tick it in the wizard (vCenter Server Running on a VM): PowerChute leaves it until the end and, once it is down, talks directly to the hosts to finish.

2. Pairing with the card

In the wizard, under Network Management Card Connection:

  • Single, Redundant or Parallel UPS: with two UPSs feeding the A and B power supplies of every host, Redundant. PowerChute only shuts down if both are on battery: losing one is no reason to stop the cluster.
  • The user and phrase must be the card's. If they don't match, PowerChute doesn't register and won't receive events.
  • On the card, the PowerChute client list shows the appliance's IP. If it isn't there, there is no pairing, whatever the PowerChute screen says.

3. The shutdown sequence

What PowerChute does with vCenter, in order, with the Virtualization Settings:

StepWhat happensSetting
1Disables vSphere HA on the clusterDisable HA on Shutdown: without it, HA may power on elsewhere the VMs that are being shut down
2VM migration (optional)Usually off: with every host on the same UPS, migrating saves nothing
3Shuts down the VMs by priority groupVM Prioritization: un-prioritised first, then low, medium and high, each group with its duration
4Shuts down vCenter (if it is a VM)Its own duration, 240 seconds by default
5Disables vCLS and puts the hosts in maintenance modeWith their own durations
6Shuts down the hostsHost Protection: which hosts and in what order
7Shuts down the PowerChute appliance and, if configured, the UPSShutdown Settings › Turn off the UPS

The priorities follow dependencies, like the layered order in the comms room UPS guide:

  • Un-prioritised (shut down first): test systems, print servers, user jump hosts.
  • Low: web applications and application servers.
  • Medium: databases, which take longer to stop cleanly.
  • High: domain controllers, DNS and whatever the others need until the end.

Each group's duration is how long PowerChute waits before moving to the next one, whether the VMs have shut down or not. Set it from how long the slowest VM in the group really takes, plus a margin. If a VM is still running when the last step's time runs out, the host goes down with it inside.

Shared storage comes after the hosts. If the array supports shutdown by command or SSH, PowerChute can launch it with a command file or an SSH action at the end; if not, it stays on until the UPS cuts its output. Confirm with the array vendor which of the two is right for it.

4. Delays and thresholds: the maths

Three numbers decide whether the sequence finishes before the battery runs out:

  • **The UPS On Battery event delay** (in Configure Events): how long to wait on battery before starting, in case power returns or the generator starts.
  • Total shutdown time: the sum of the steps in section 3, plus two minutes PowerChute reserves for the operating system itself.
  • Low Battery Duration (on the card, UPS › Configuration › Shutdown): the minutes left when the UPS declares low battery. When that point is reached, PowerChute starts even if the delay hasn't finished.

With an example from the room:

ItemValue
Measured runtime with the current load22 min
Durations: un-prioritised 2 min, low 3, medium 6, high 314 min
vCenter, vCLS and maintenance mode6 min
System margin2 min
Total shutdown time22 min

It doesn't fit: with any delay on battery, the sequence doesn't finish. PowerChute flags it with the Available runtime has been exceeded event, and rightly so. The ways out are reducing durations (measured, not guessed), taking load off the UPS or starting earlier. Here, after measuring, the low group ended up at 2 minutes and the medium one at 4, vCenter at its real duration (3 minutes, one less than the default) and the On Battery delay at 1 minute: 1 + 18 = 19 minutes out of 22.

  • Runtime Remaining Below Threshold: besides the delay, an event that starts the shutdown when the remaining runtime drops below a threshold, however long it has been on battery. Useful if the load changes a lot during the day.
  • The card's Low Battery Duration must be longer than the total shutdown time, with a margin. If it is shorter, the UPS cuts its output with the sequence half done.

5. PowerChute on a physical Windows server

For servers that aren't hosts (the physical backup server, for example), PowerChute is installed on Windows itself with the vendor's installer and configured the same way, at https://srv-bkp-01:6547.

  • The same wizard: UPS, protocol, card IP, user and phrase.
  • In Configure Events, UPS On Battery with Shut Down System and its delay, coordinated with the cluster: a backup server can shut down before anything else.
  • If something needs stopping carefully before shutdown (the backup service, a database), a command file in Shutdown Settings, with its duration. PowerChute only runs files from the user_files folder of its installation.
  • Windows Firewall: TCP 6547 and TCP/UDP 3052 from the card's IP.

6. A controlled test

An untried configuration is a hypothesis. Once a year, and after every big change to the cluster:

  1. Before: a window agreed with the application owners and with the UPS maintainer present, a recent backup, and the list of VMs without VMware Tools running:
  1. The cut: the maintainer opens the UPS input (nobody pulls a host's power cable). Someone notes the time of each step from the vCenter console and the PowerChute event log.
  2. During: check that each group shuts down in its turn, that vCenter goes down after all the VMs and that the hosts shut down with every VM already off.
  3. Coming back: the input is closed, the UPS recharges and hosts, storage and VMs are powered on in reverse order (PowerChute can start the VMs when power returns if configured to). The owners check their applications.
  4. After: compare the real times with the configured durations and adjust.

7. The case: "in the test, the hosts shut down before the VMs"

Saturday, 22:00, annual test. After 9 minutes the three hosts are off; on the way back, the srv-sql-02 database starts with recovery and the licence server has its file system marked dirty.

  1. The PowerChute log tells you what happened: the medium group had the default 120-second duration and PowerChute moved on with srv-sql-02 still shutting down. In vCenter, the Initiate guest OS shutdown task for srv-sql-02 started at 22:04:10 and the VM was still running at 22:08, when host shutdown began.
  2. The VMs without Tools: srv-lic-01 and app-legacy-02 were on the list from step 1 of the test. Without VMware Tools there is no clean shutdown: they were powered off hard at the start.
  3. HA: Disable HA on Shutdown was unticked. When the first host shut down, HA restarted two VMs on the other two, which went down again two minutes later with their host.
  4. The card: Low Battery Duration was at 2 minutes, the factory value on many models. It made no difference because the test was cut short, but in a long outage the UPS would have cut its output with the sequence half done.

What was changed:

  • Measured durations: each group's is the slowest shutdown among its VMs (srv-sql-02 takes 4 minutes 20 seconds) plus one minute.
  • VMware Tools installed on both VMs, and the report of VMs without Tools added to the monthly review.
  • Disable HA on Shutdown ticked.
  • Low Battery Duration raised to cover the total shutdown time, and the maths in section 4 recalculated with no Available runtime has been exceeded event.
  • A second test in the next window: hosts off at 17 minutes with every VM shut down before them and no start-up with recovery.

In the report: the test timeline, what failed, the changes and the second test that confirms them.
