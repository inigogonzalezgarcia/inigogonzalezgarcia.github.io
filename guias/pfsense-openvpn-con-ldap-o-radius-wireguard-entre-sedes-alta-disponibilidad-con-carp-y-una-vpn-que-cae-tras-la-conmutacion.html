pfSense: OpenVPN for users with LDAP or RADIUS, WireGuard between sites, high availability with CARP, backups and upgrades, and a VPN that drops after failover

Remote access and resilience for an office pfSense: OpenVPN with Active Directory users over LDAP or RADIUS with MFA, WireGuard to another site, two firewalls in high availability with CARP, pfsync and XMLRPC sync, backups and upgrades without an outage, and the VPN that drops after failover with both nodes MASTER.

Level 3 · pfSense: office firewall · 7 min read · Updated 6 Nov 2026

Rather practise it?Solve the simulated ticket "The secondary firewall does not take over" in SysAdmin Desks ↗

What you'll get

People working from outside with their domain account, the other site reaching the servers through a tunnel, and the office keeping its internet even if a firewall fails or reboots for an upgrade. And knowing what to look at when, after a failover, the VPN does not come back.

Before you start

  • The pfSense from the pfSense as the office firewall guide, with its VLANs, aliases and rules.
  • For high availability, two identical boxes (same hardware, same interface names, same version) and a third network card for synchronisation. On the WAN, three public IPs: one per node and a shared one (a /29 from the ISP).
  • In Active Directory: a VPN-Usuarios group, a service account to query LDAP and the company CA (for LDAPS). For MFA, an NPS server with the Entra MFA extension.
  • A public name for the VPN: vpn.contoso.example.

1. Domain users: LDAP or RADIUS

First, the company CA under System › Certificates › Authorities › Add (import the root CA certificate). Then the authentication server:

  • The extended query lets in only members of VPN-Usuarios: disabling the account in AD or removing it from the group cuts the VPN.
  • Test it in Diagnostics › Authentication with one user inside the group and one outside before building the VPN.
  • With RADIUS (for MFA): type RADIUS, the NPS IP, the shared secret, port 1812 and an Authentication Timeout of 60 seconds. With the default (5 seconds) the connection fails while the user is still approving the push on their phone.

2. OpenVPN for users

VPN › OpenVPN › Wizards, with the authentication server from step 1. The values that matter:

  • A Local Network with only the networks people should reach is split tunnelling: the rest of the laptop's traffic uses its own connection. To force everything through the office, Redirect IPv4 Gateway.
  • The wizard's rule on the OpenVPN tab lets everything through: replace it with alias-based rules, as on the VLANs.
  • The clients: the openvpn-client-export package and VPN › OpenVPN › Client Export. Under Host Name Resolution, Other with vpn.contoso.example: that way the file does not carry the IP of a specific node (it matters in step 6).

3. WireGuard between sites

The WireGuard package (Package Manager) and, under VPN › WireGuard:

  1. In Interfaces › Assignments, assign tun_wg0 as an interface (WG_BILBAO), with static IP 10.99.1.1/30.
  2. In System › Routing › Gateways, a gateway 10.99.1.2 on that interface and, under Static Routes, 10.30.0.0/16 through it.
  3. Rules: on WAN, allow UDP 51820 only from 198.51.100.20; on the WG_BILBAO tab, whatever the other site may use, with aliases.

Allowed IPs works both as a route list and as a filter: a packet from a network not in the list is simply dropped.

4. High availability: CARP, pfsync and XMLRPC

Two nodes, fw-a (primary) and fw-b (secondary), with a SYNC interface cabled between them (10.20.98.1 and 10.20.98.2). On each network, each node has its own IP and they share a CARP virtual IP, which is the one devices use as their gateway:

Networkfw-afw-bCARP (VIP)
WAN203.0.113.11203.0.113.12203.0.113.10
USUARIOS10.20.20.210.20.20.310.20.20.1
SERVIDORES10.20.10.210.20.10.310.20.10.1

Then, on fw-a only, System › High Availability:

  • State Synchronization (pfsync): Synchronize states ticked, Synchronize Interface SYNC, pfsync Synchronize Peer IP 10.20.98.2. Open connections move to the other node without being cut.
  • Configuration Synchronization (XMLRPC): Synchronize Config to IP 10.20.98.2, an administrator account on the secondary, and what to sync (rules, NAT, aliases, virtual IPs, OpenVPN, certificates, users, authentication servers, DHCP). When it syncs, fw-b receives the virtual IPs with Skew 100 and stays as the backup.
  • On SYNC, a rule allowing everything between the two nodes.
  • Outbound NAT in hybrid mode, translating to the WAN VIP (203.0.113.10), not to each node's IP; and in DHCP, gateway and DNS = the VIP.

Status › CARP shows MASTER on fw-a and BACKUP on fw-b. To test, Enter Persistent CARP Maintenance Mode on fw-a: everything moves to fw-b without breaking a download in progress.

5. Backups and version upgrades

  • Diagnostics › Backup & Restore: Download configuration as XML, with Encrypt this configuration file ticked (it holds keys and certificates). The Config History on the same page keeps earlier versions and lets you compare and roll back.
  • Services › Auto Config Backup: an automatic encrypted copy to Netgate's service after every change. The encryption key goes in the password manager: without it the backup is useless.
  • Upgrading: System › Update, reading the release notes first and checking that the installed packages have a compatible version. With high availability, fw-b first; once it is fine, maintenance mode on fw-a, upgrade it and leave maintenance mode.

6. The ticket: "after the firewall upgrade, the VPN does not come back"

Thursday, 22:30, upgrade window. fw-b is upgraded, then fw-a with maintenance mode. From then on, remote workers cannot connect and in the office the network works on and off.

First symptom: both nodes MASTER. Status › CARP on fw-b says MASTER, and on fw-a, now out of maintenance, too. Both boxes answer for 10.20.20.1 and devices flip between them: hence the "on and off" network.

  1. Each node thinks it is alone because it does not receive the other's CARP advertisements (IP protocol 112 to 224.0.0.18). In Diagnostics › Packet Capture on USUARIOS, protocol CARP: only the node's own advertisements show up.
  2. Usual causes: the VLAN is missing from the switch trunk of one of the nodes; the switch filters multicast; the virtual IPs on fw-a and fw-b have a different password or VHID (Status › System Logs › System shows CARP messages about an incorrect hash); or, on virtual machines, the virtual switch does not allow MAC changes or forged transmits.
  3. Here it was the switch: the afternoon's change had left VLAN 20 off fw-b's trunk. Once fixed, fw-b goes back to BACKUP.

Second symptom: the VPN. The OpenVPN server had been created with Interface: WAN, fw-a's own IP (203.0.113.11), and the exported files pointed to that IP. With fw-a in maintenance, clients were calling a node that was not serving them.

  • On the OpenVPN server, Interface: the WAN VIP (203.0.113.10). With XMLRPC, the configuration goes to fw-b; the service only answers on the node holding the VIP.
  • vpn.contoso.example resolves to 203.0.113.10 and the clients are exported again with that name. Those that already had the name reconnect on their own through the keepalive.
  • WireGuard does not bind to an IP: after leaving maintenance mode, the other site may keep talking to the node that is no longer MASTER. A node reboot does not cause it; maintenance mode does. After each maintenance, check the handshake in Status › WireGuard and restart the service if needed.

In the ticket: each node's CARP state before and after, the cause (switch trunk), the OpenVPN interface change and the test: maintenance mode on fw-a with a VPN session open and a continuous ping to the other site.
