Cisco: secure management with AAA and RADIUS, SSH only, SNMPv3, syslog, authenticated NTP and nobody can log in after aaa new-model

AAA new-model with RADIUS (NPS or FreeRADIUS) and a local emergency account, SSH v2 and access-class on the VTY lines, SNMPv3 without communities, syslog with levels and local time, keyed NTP, login banner, exec-timeout, archive with change logging and how to get back in when the switch rejects everyone.

Level 2 · Cisco: first commands on a switch · 12 min read · Updated 6 Nov 2026

What you'll get

Leaving the management of a Cisco switch or router the way an audit expects it: named users against RADIUS with a local emergency account, SSH v2 only and only from the management network, SNMPv3 instead of communities, logs on a syslog server with the right time on them, keyed NTP, a login banner and sessions that close themselves, and a copy of every change with who made it. And knowing how to get back in when, after enabling aaa new-model, the switch says Authentication failed to everyone. The first commands and config backup guide covers getting in and the manual backup; this one starts from there.

Before you start

  • Console access to the device (cable or console server) and a second SSH session that stays open until you have checked the change: this is about how you get in.
  • IOS XE 17.x (Catalyst 9200/9300, ISR 1000/4000). The radius server syntax is the current one; on old IOS releases you will see radius-server host.
  • A RADIUS server (NPS on Windows Server or FreeRADIUS 3.2) with the switch registered as a RADIUS client: its source IP and a shared secret.
  • The site's data: management network 10.10.0.0/24 on Vlan10, RADIUS 10.10.0.20 and 10.10.0.21, monitoring 10.10.0.30, syslog 10.10.0.31 and NTP 10.10.0.5 and 10.10.0.6.
  • An approved change and reload in 10 before you start, as explained in the VLANs, trunks and remote changes guide.

1. Local emergency account and SSH v2

First, the local account: if you enable AAA without it and RADIUS does not answer, nobody is left who can log in.

  • algorithm-type scrypt stores the password as type 9. Never password (type 7, reversible) for users or enable.
  • adm-local is the emergency account: its password goes into the network team's password vault, not into daily use.
  • login block-for blocks logins for 120 seconds after 5 failures within a minute: it slows down anyone guessing passwords.
  • service password-encryption only hides from view the keys that stay as type 7 (such as the RADIUS key). It is not real encryption.

2. AAA with RADIUS and local fallback

  • The order of the list matters: RADIUS first and, only if no server answers, the local database. If RADIUS replies Access-Reject (wrong password, user outside the group), the switch does not try local. The local account is for when RADIUS is down, not a second attempt.
  • The console uses its own list, CONSOLA, local only: if RADIUS is misconfigured, the console cable still works.
  • ip radius source-interface Vlan10 fixes the source IP. That is the IP that has to be registered in NPS or FreeRADIUS.
  • deadtime 10: a server that does not answer is set aside for 10 minutes and the switch does not wait for it on every login.
  • Privilege level: aaa authorization exec asks RADIUS which level each user gets. In NPS, in the network policy for the GG-Red-Admins group: Settings › Vendor Specific › Cisco-AV-Pair with the value shell:priv-lvl=15. In FreeRADIUS, the attribute Cisco-AVPair = "shell:priv-lvl=15" in the reply. Without it, the user lands in > mode.

3. VTY lines: SSH only, and only from the management network

  • transport input ssh shuts out Telnet. access-class limits where from: a user's desk does not even see the username and password prompt. deny any log leaves in the log who tries.
  • show line tells you how many VTY lines the device has; the ACL and the transport go on all of them, or the last one stays open.
  • exec-timeout 10 0 closes the session after 10 idle minutes, on the console too.
  • The banner gives nothing away: no model, no version, no "welcome".
  • Without the IOS XE WebUI, no ip http server and no ip http secure-server: one less exposed service.

4. SNMPv3 without communities

An SNMPv2c public community travels in clear text and gives read access to anyone who guesses it. SNMPv3 with authPriv authenticates and encrypts:

  • The group says what can be seen (the view) and from where (the ACL); the user holds the keys. A read-only group: monitoring does not need to write.
  • SNMPv3 users do not appear in show running-config: their keys are stored tied to the device's engine ID. A backup restored onto another switch does not bring them; they are created again.
  • From the monitoring server: snmpwalk -v3 -l authPriv -u zabbix -a SHA -A <auth-key> -x AES -X <priv-key> 10.10.0.11 sysName.0. If it answers, the Zabbix or SolarWinds template can use the same credentials.

5. Syslog, levels and the time on each message

LevelNameExample
0-2emergencies, alerts, criticalpower supply failure, temperature
3errorsa port in err-disabled
4warningsa neighbour going down
5notificationsa port going up or down, a configuration change
6informationalACL denies, SSH logins
7debuggingonly during troubleshooting, never to the server
  • logging trap sets the level sent to the server: that level and every more severe one. informational is the usual choice.
  • Without service timestamps ... localtime, each message carries the time since boot (3w2d:) or UTC, and matching the switch log against a server's becomes guesswork.
  • logging console critical stops the console filling up with messages while you work on it.

6. NTP with authentication

The time has to come from a trusted source: with a key, the switch drops replies from any other device pretending to be the server.

  • The NTP server must have the same key under the same number (in chrony, in its key file). Some IOS XE releases accept stronger algorithms than MD5: ntp authentication-key 1 ? lists them; use the strongest both ends support.
  • Domain controllers running the Windows Time service do not offer this kind of key authentication. For network equipment, a Linux NTP server, the firewall or the network core.
  • authenticated on each association is the proof. If it says insane or unsynced, the key or its number do not match.

7. Archive: a copy of every change and who made it

  • write-memory saves a copy in flash:archive/ every time someone saves, and time-period 1440 one a day even if nobody does. maximum 14 keeps the last 14.
  • log config records every configuration command with the user who typed it, and notify syslog sends it to the syslog server: the change log no longer depends on someone writing it down. hidekeys keeps passwords out of the log.
  • Rolling back: configure replace flash:archive/SW-P1-01-3 list applies that copy and shows the lines it changes.
  • The flash copy does not replace the off-device backup: path also accepts scp:// to the backup server, or you keep the central tool (Oxidized, RANCID) that already collects the configuration.

8. The ticket: "since last night's change nobody can log in to SW-P1-01"

Tuesday, 8:10. Last night's change applied the AAA template to SW-P1-01. Now every technician, with their own user and with adm-local, gets % Authentication failed. Nobody left a session open or scheduled reload in. The switch still serves the floor: only the management door has closed.

  1. What RADIUS says: on the NPS server, Event Viewer › Windows Logs › System, source NPS, event 13: A RADIUS message was received from the invalid RADIUS client IP address 10.10.99.2. The switch does not send from Vlan10 but from the interface closest to the server, and that IP is not registered. NPS drops the request without answering. With FreeRADIUS, radiusd -X shows *Ignoring request to auth address * port 1812 ... from unknown client 10.10.99.2*.
  2. Why adm-local does not work either: the applied configuration says aaa authentication login default group RAD-GESTION, without local, and the console has no list of its own. With RADIUS not answering, there is no method left.
SymptomCauseFix
Nobody gets in, NPS event 13The source IP is not a RADIUS clientip radius source-interface Vlan10 or register that IP

Getting back in without a reboot: temporarily register IP 10.10.99.2 as a RADIUS client in NPS, with the same secret. Named users get in straight away. From inside, fix the template:

Once the test passes from the management IP, delete the temporary client from NPS.

If RADIUS cannot be touched: what is left is password recovery on the console, with a reboot and an outage for the floor (emergency window). On a Catalyst 9200/9300: hold the Mode button during boot until the switch: prompt, SWITCH_IGNORE_STARTUP_CFG=1 and boot. Once in, copy startup-config running-config, fix AAA, no system ignore startupconfig switch all in global configuration and save.

If someone has disabled password recovery (no service password-recovery), the only way is to erase the configuration. That is why an off-device configuration backup is not optional.

In the ticket: time of the change, the NPS event with the source IP, the cause (source IP and a list without local), the fix, the test and the removal of the temporary client. And in the template: local at the end of the list, a dedicated console list and reload in 10 on every AAA change.
