Windows Server: file shares and NTFS permissions with PowerShell, AGDLP groups, an audit report and an access denied with the user already in the group

Share permissions versus NTFS permissions, the AGDLP model, New-SmbShare with access-based enumeration, icacls, Get-Acl and Set-Acl, inheritance and its exceptions, a permissions report to CSV for the audit, and the user who is in the right group and still gets access denied.

Level 2 · Windows Server · 9 min read · Updated 6 Nov 2026

What you'll get

Shared folders that make sense at a glance: who gets into each one is decided by adding or removing a person from a group, never by touching the folder, and every quarter a CSV comes out with the permissions you can hand to audit without editing it by hand. And, when someone says "you've already added me to the group and I still can't get in", knowing within five minutes whether it is their session, a deny permission or the share.

Before you start

  • A Windows Server 2022 or 2025 file server, here srv-files01, with the File Server role: Install-WindowsFeature FS-FileServer.
  • The data on its own volume (D:), not on C:.
  • The Active Directory module on the machine you work from (RSAT-AD-PowerShell) and rights to create groups in OU=Groups,DC=contoso,DC=local.
  • Knowing which departments and folders exist. A simple table (folder, business owner, who reads, who modifies) avoids half the arguments.

1. Two layers: the share and NTFS

When someone opens \\srv-files01\Finance, Windows checks two permission lists and applies the most restrictive:

LayerWhere you see itLevelsApplies
Share permissionGet-SmbShareAccess, Properties › Sharing › Advanced SharingRead, Change, Full ControlOnly when coming in over the network
NTFS permissionGet-Acl, icacls, Properties › SecurityRead & execute, Modify, Full control, special permissionsOver the network and locally, folder by folder
  • With Change on the share and Read on NTFS, the user can only read. With Full Control on the share and Modify on NTFS, they can modify.
  • The fine detail always goes in NTFS: the share doesn't distinguish subfolders.
  • Full Control for administrators only. A user with Full Control can change the permissions and take ownership of the folder.

2. Groups with AGDLP

AGDLP: Accounts go into Global groups by role, global groups go into Domain Local groups by resource and permission, and the Permission is granted only to the domain local group.

  • The name says what it is: DL (domain local), FS (file server), the folder and the permission (M modify, R read). The path goes in the description.
  • A new person in Finance joins GG-Finance on their first day and already has every folder in the department. Nobody touches NTFS permissions.
  • If tomorrow Audit needs to read Finance, GG-Internal-Audit is added to the R group. The list of who accesses what comes from the group members.

3. The share with New-SmbShare

  • With no access parameters, New-SmbShare grants Read to Everyone. Always pass it the groups.
  • Many organisations leave the share with Authenticated Users: Change and all the control in NTFS. Putting the same groups in both layers is more work, but the audit report comes out clearer.
  • -FolderEnumerationMode AccessBased turns on access-based enumeration: each user only sees the subfolders they can open. It isn't a permission, it is courtesy: whoever doesn't see the Payroll folder doesn't call to ask why they can't get in.
  • -CachingMode None turns off offline files on that share; turn them on only where they are needed.
  • To change things later: Grant-SmbShareAccess, Revoke-SmbShareAccess and Set-SmbShare -FolderEnumerationMode AccessBased on an existing one.

4. NTFS permissions: icacls, Get-Acl and inheritance

The Finance root folder doesn't inherit from D:\Data. Inheritance is cut and explicit permissions are set. icacls accepts SIDs with an asterisk, which work in any Windows language: *S-1-5-18 is SYSTEM and *S-1-5-32-544, Administrators.

  • (OI)(CI): the permission is inherited by files (object inherit) and subfolders (container inherit). Without it, it only applies to the folder.
  • /inheritance:r removes what is inherited; /inheritance:d turns it into explicit entries so you can edit them. /grant:r replaces whatever that group had instead of adding to it.
  • /save before touching anything: if you get it wrong, icacls D:\Data /restore C:\Temp\acl-finance-before.txt puts it back (it is restored onto the parent folder).

An exception inside the folder (Payroll, only for its group) is done the same way: inheritance cut on that subfolder, with its own DL-FS-Payroll-M. Each exception is one more line in the report: keep them few.

5. The permissions report for the audit

What audit asks for is who can do what in each folder. Inherited rules repeat the parent folder: the useful report only lists the explicit ones, that is, where a decision was made.

  • Two CSVs: which group has which permission and who is in each group. Together they answer "who can delete in Payroll?".
  • -Depth 3: below that there are almost never exceptions, and walking a whole volume with millions of files takes hours. Folders only, never files.
  • The folders with no access file matters: a folder not even the administrator can read is usually one someone took ownership of with everyone else locked out.
  • A numeric value in Rights (for example 268435456) is a generic right, common on CREATOR OWNER; it isn't an error.
  • If a person's account appears directly under Account, it is an exception to the AGDLP model: it moves to its group and is removed.

6. The ticket: "I'm already in the group and I still get access denied"

Tuesday, 10:20. Lucía Martín (lmartin) joined Finance today. At 10:00 she was added to GG-Finance. Opening \\srv-files01\Finance: You do not have permission to access \\srv-files01\Finance.

  1. Is she really in the group? Get-ADGroupMember DL-FS-Finance-M -Recursive | Where-Object SamAccountName -eq lmartin. If she shows up, the AD side is fine.
  2. Does her session know? Groups travel in the token, created at sign-in, and in Kerberos tickets, which last up to 10 hours. On her computer:

If whoami shows neither GG-Finance nor DL-FS-Finance-M, her session predates the change. klist purge deletes the Kerberos tickets and the next access requests a new one with the current groups, but whoami will still show the sign-in token: signing out and back in is the safe option. And on the server, the SMB session already open keeps the old token:

  1. A deny rule? An explicit deny beats any explicit allow. On the folder, Properties › Security › Advanced › Effective Access, with her user: it shows the result of both layers and which rule blocks it. Or with PowerShell: (Get-Acl D:\Data\Finance).Access | Where-Object AccessControlType -eq 'Deny'. Here it was: someone had set Deny for GG-Interns, and Lucía had been an intern and was still in that group.
  2. The share? Get-SmbShareAccess -Name Finance: if DL-FS-Finance-M isn't there and only groups she isn't in are listed, NTFS is never even checked.
  3. Only one subfolder? If she gets into Finance but not Closings, that subfolder has inheritance cut and doesn't include her group: icacls D:\Data\Finance\Closings.

The fix here: remove Lucía from GG-Interns (her move to Finance should have done it), replace the Deny with simply not granting the permission, close her SMB session and have her sign in again. In the ticket: group, cause (deny from an old group), change and a check with Effective Access.

Don't use Deny to remove access. Remove the person from the group that grants the permission. Deny rules get forgotten and years later block someone nobody can explain.
