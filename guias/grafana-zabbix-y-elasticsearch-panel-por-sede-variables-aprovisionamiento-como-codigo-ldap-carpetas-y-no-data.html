Guides · Level 3

Grafana over Zabbix and Elasticsearch: a per-site operations dashboard with variables, data sources and dashboards as code, LDAP with roles by group, folders with permissions and a "No data" for one site

The Zabbix plugin with an API token and an Elasticsearch data source, an operations dashboard with the site as a variable (problems, latency, traffic and log errors), data sources and dashboards provisioned from files in Git, sign-in with Active Directory and the role set by group, folders with per-team permissions, and what to check when one site comes up blank.

Level 3 · Grafana · 9 min read · Updated 6 Nov 2026

What you'll get

A single dashboard, Operations per site, where you pick the site at the top and see its open problems in Zabbix, the latency and traffic of its line, and its servers' errors in Elasticsearch. With data sources and dashboards stored as files in Git (if Grafana is reinstalled tomorrow, it is back in minutes), sign-in with the Active Directory account and the right role by group, and folders where each team edits its own.

Before you start

  • Grafana 12 (or 13) installed from the official repository on Linux, with configuration in /etc/grafana/ and the grafana-server service. The Prometheus data source, the first panel and alerts to the channel are in the Grafana: first panel and alert guide.
  • Zabbix 7.0 LTS with each site's hosts in a group Sedes/Madrid, Sedes/Bilbao, Sedes/Valencia (the Zabbix guide covers the server, templates and groups).
  • Elasticsearch 8 or 9 with logs in the logs-* data streams and a field with the site in every document, here labels.sede (the ELK and Kibana guides).
  • In Active Directory, a service account to query the directory (svc-grafana-ldap, unprivileged) and three groups: GRP-Grafana-Admins, GRP-Grafana-Editores and GRP-Grafana-Lectores.

1. The Zabbix plugin and data sources as code

The plugin is an app (alexanderzobnin-zabbix-app) that includes the data source; install it on the Grafana server and restart the service:

In Zabbix, a grafana user in a user group with read permission on the Sedes/* groups and, for that user, a token in Users › API tokens › Create API token. In Elasticsearch, a grafana_reader user with a role that has read and view_index_metadata on logs-*.

The data sources are not created by hand in the UI but with a provisioning file:

  • Secrets do not go in the file: $ZABBIX_API_TOKEN and $ES_GRAFANA_PASSWORD are read from the service environment, in /etc/default/grafana-server (Debian and Ubuntu) or /etc/sysconfig/grafana-server (RHEL), with 0640 permissions and owned by root:grafana.
  • The fixed uid is what matters: dashboards store the data source by its uid, so the same JSON works in production and on a fresh install.
  • trends: true makes the plugin read Zabbix trends (hourly averages) instead of full history for ranges over 7 days: 30-day panels load in seconds.
  • The internal CA in the system store (update-ca-certificates) so Grafana trusts the Zabbix and Elasticsearch certificates.

2. The per-site dashboard: variables and queries

In the new dashboard, Edit › Settings › Variables › Add variable:

  • The variable's regex keeps what comes after Sedes/: the variable is Madrid, Bilbao or Valencia, the same text labels.sede carries in the logs.
  • A second variable, equipo, of type Query on Zabbix with Query type: Host, Group: Sedes/$sede and Host: /.*/, with Multi-value and Include All option.
  • To pick servers from the logs, a variable on Elasticsearch with the query {"find": "terms", "field": "host.name", "query": "labels.sede:$sede"}.

The panels, each with its query:

PanelSourceQuery
Open problemsZabbixQuery type: Problems, Group Sedes/$sede, Host $equipo, minimum severity Average
Line latencyZabbixMetrics, Group Sedes/$sede, Host $equipo, Item ICMP response time
WAN trafficZabbixMetrics, Item /Interface .*WAN.*: Bits .*/
Log errorsElasticsearchQuery labels.sede:"$sede" AND log.level:error, metric Count, grouped by Terms host.name and Date histogram

Expressions between slashes (/.../) are regular expressions in the Zabbix plugin: a single panel collects every WAN interface of the site's devices. With everything in place, Export › Export as JSON and the file goes to the repository (step 3).

One site per view is what reads well on an on-call screen. To compare sites, another row with Repeat for: sede and the variable set to Multi-value.

3. Dashboards provisioned from Git

A grafana-config repository with the same layout as /etc/grafana/ and /var/lib/grafana/dashboards/:

  • foldersFromFilesStructure: true creates a folder in Grafana for each subfolder of the repository: Operaciones and Redes.
  • Dashboards are re-read every 60 seconds; data sources, when the service restarts or with curl -X POST -u admin https://grafana.contoso.local/api/admin/provisioning/datasources/reload.
  • With allowUiUpdates: false, Grafana will not save changes to a provisioned dashboard. The flow: edit in the UI, Export as JSON, commit on a branch, review and deploy (git pull on the server or the pipeline). The dashboard's change history is Git's.
  • Before exporting, check the JSON has a fixed dashboard uid: it is what keeps people's links and bookmarks working.

4. Active Directory: sign-in and role by group

In /etc/grafana/grafana.ini:

  • The first matching mapping wins, top to bottom: that is why Admin goes first. If someone is in two groups, they get the higher role.
  • The group_search_filter with 1.2.840.113556.1.4.1941 resolves AD nested groups: if GRP-Redes is inside GRP-Grafana-Editores, its members sign in as Editor.
  • Without a group_dn = "*" at the end, anyone not in one of the three groups cannot sign in. That is what you want.
  • The role is recalculated at every sign-in: removing someone from the group in AD lowers their role the next time they sign in.
  • Administration › Authentication › LDAP shows the connection status with the domain controllers and lets you test a user to see which groups and role they would get, without them having to sign in.

Keep a local admin account with a long password in the vault. If LDAP fails, it is the only way in to fix it.

5. Folders and permissions

The organisation role (Viewer, Editor, Admin) is global. The fine-grained part is per folder: Dashboards › folder › Folder actions › Manage permissions.

FolderPermissions
OperacionesViewer role: View. Operaciones team: Edit
RedesViewer role: View. Redes team: Edit
DirecciónRemove the Viewer role's permission; Dirección team: View
  • Teams are created in Administration › Users and access › Teams. In Grafana OSS they are filled in by hand or via the API; automatic team sync with LDAP groups (team sync) is a Grafana Enterprise and Grafana Cloud feature.
  • With provisioned dashboards, Edit on the folder lets people change and explore, but the final change goes through Git (step 3).
  • Folder permissions cannot be set in provisioning files; if you also want them as code, the Grafana Terraform provider or the API.

6. The ticket: "on the operations dashboard, Bilbao comes up blank"

Monday, 8:45. The on-call team reports: when they pick Bilbao, the problems, latency and traffic panels show No data; Madrid and Valencia look fine. The log errors panel does have data.

No data means the query worked and came back empty. If Grafana could not reach the source, the panel would show a red triangle with the error. The problem is in what is being asked, not in the connection.

  1. What Grafana asks: on the latency panel, panel menu Inspect › Query › Refresh. The host.get response for the Sedes/Bilbao group is an empty list: Zabbix returns no hosts in that group.
  2. In Zabbix: Data collection › Host groups, the Sedes/Bilbao group shows 0 hosts. The hosts are in Discovered hosts. Last week the Bilbao proxy was replaced and the hosts were registered again through autoregistration, whose action only adds them to that group.
  3. Fix: in Bilbao's autoregistration action, operation Add to host groups: Sedes/Bilbao, and the current hosts are moved with a mass update. Grafana caches Zabbix responses for the cacheTTL (1 hour); to see it straight away, restart grafana-server.

The other causes of No data for a single site:

WhereCauseHow it shows
ZabbixThe grafana user group has no read permission on the new groupThe site is missing from the variable, or shows with no hosts
ZabbixThat site's template uses a different item name (ICMP ping versus ICMP response time)Inspect: hosts yes, items no
Elasticsearchlabels.sede is spelled differently (bilbao versus Bilbao): keyword fields are case-sensitiveIn Explore, labels.sede:* grouped by value shows both spellings
ElasticsearchThe site's agents do not set labels.sedeIts servers' logs are there, but without that field
BothThe site's servers have their clock running aheadThe data exists, but outside the panel's time range

In the ticket: panel, site, what the query returned (Inspect), the cause in the source and the change. And in the procedure for adding a new site, one more step: check it on this dashboard.
