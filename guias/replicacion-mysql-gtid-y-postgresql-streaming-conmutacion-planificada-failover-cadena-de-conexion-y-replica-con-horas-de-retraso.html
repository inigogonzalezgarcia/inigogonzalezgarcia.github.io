Replication and failover: MySQL 8.4 with GTID, PostgreSQL streaming replication, lag, switchover versus failover, the connection string and a replica hours behind

Building a MySQL 8.4 replica with GTID and a PostgreSQL 17 standby with pg_basebackup and a replication slot, measuring lag in seconds and in bytes, a planned switchover without losing transactions, what changes in a failover, what the application connection string needs, and a replica that is hours behind or has stopped with an error.

Level 3 · PostgreSQL, MySQL and SQL Server · 11 min read · Updated 6 Nov 2026

What you'll get

A second live copy of the database that is up to date, that you know how to measure and that you can turn into the primary in a maintenance window (or in an emergency) without improvising. In MySQL, with GTID; in PostgreSQL, with streaming replication and a slot. And the part that tends to be forgotten: the application knowing which server to connect to after the change.

Before you start

  • Two servers with the same engine version: MySQL 8.4 LTS (srv-db-01a 10.20.40.11 and srv-db-01b 10.20.40.12) and PostgreSQL 17 (srv-db-02a 10.20.40.21 and srv-db-02b 10.20.40.22), on Ubuntu 24.04.
  • The engine port open between the two servers (3306 or 5432), not only from the application.
  • Accounts, the scheduled backup and the quick look at replica status are in the least privilege and backups guide; the MySQL versus MariaDB naming table and the duplicate-key error, in the MySQL and MariaDB one. They are not repeated here.

A replica is not a backup. A DROP TABLE on the primary reaches the replica in milliseconds. Backups still have to run.

1. MySQL 8.4: a replica with GTID

With GTID every transaction has a unique identifier (server-uuid:number). The replica knows which transactions it has and asks for the ones it lacks, with no files or positions to note down. On both servers, in /etc/mysql/mysql.conf.d/mysqld.cnf:

  • The binary log is already on in MySQL 8. binlog_expire_logs_seconds (7 days here; 30 by default) is how long the replica can be stopped and still catch up on its own. Beyond that, it has to be rebuilt.
  • On Ubuntu, bind-address ships as 127.0.0.1: the replica could not connect.

The replica starts from a copy of the primary that includes the set of GTIDs already applied:

RESET BINARY LOGS AND GTIDS (formerly RESET MASTER) empties the replica's GTID history so the dump can set its own. On the replica only, never on the primary. With databases of hundreds of GB, the clone plugin (CLONE INSTANCE FROM ...) copies the files directly and is much faster.

2. PostgreSQL 17: a standby with streaming replication

The standby receives the primary's WAL (the change log) in real time and applies it; it can be queried read-only. On the primary:

On Ubuntu the configuration lives in /etc/postgresql/17/main/, outside the data directory, so it is not copied to the standby: keep both files identical on both servers (that is why pg_hba.conf already has both IPs).

On the standby, the data directory is replaced by a copy of the primary with pg_basebackup:

  • -R creates standby.signal and writes primary_conninfo and primary_slot_name to postgresql.auto.conf: the server starts as a standby.
  • -C -S srv_db_02b creates a replication slot on the primary: the primary keeps the WAL the standby has not yet received, even if it is stopped for a few hours. max_slot_wal_keep_size sets the limit so a dead standby does not fill the primary's disk.

3. Measuring lag

Basic status (threads on Yes, pg_stat_replication) is in the backups guide. What a production replica adds is measuring how much and what is being retained:

  • wal_status moves from reserved to extended and unreserved when the slot retains a lot; lost means the standby can no longer catch up on its own.
  • In MySQL, Seconds_Behind_Source compares the time of the transaction being applied: with a huge transaction it jumps from 0 to hours at once. The reliable figure is which GTIDs are missing: SELECT GTID_SUBTRACT('<primary gtid_executed>', @@GLOBAL.gtid_executed); on the replica. Empty means it is up to date.
  • Monitoring alerts: lag over 5 minutes, a stopped thread, a slot that is inactive or retaining more than 10 GB.

4. Planned switchover versus failover

Planned switchoverFailover
WhenPatching or replacing the primary's hardwareThe primary is down and will not be back soon
Data lossNone: you wait for the replica to have everythingWhatever had not reached the replica (asynchronous replica)
The old primaryBecomes a replica of the new oneCannot come back as primary: it is rebuilt or rejoined
Who decidesScheduled changeThe application owner, knowing what may be lost

MySQL, planned switchover (application in maintenance):

SET PERSIST stores the value in mysqld-auto.cnf, which takes precedence over mysqld.cnf: after a restart, each server keeps its role. Update the comments in mysqld.cnf too so the next person who reads it is not misled.

PostgreSQL, planned switchover:

  1. Application in maintenance. On the primary, sudo systemctl stop postgresql@17-main: the normal (fast) shutdown sends all pending WAL to the connected standby, including the final checkpoint.
  2. On the standby, promote it: sudo -u postgres psql -c "SELECT pg_promote();" returns t and pg_is_in_recovery() becomes f.
  3. On the new primary, the slot for the old one: SELECT pg_create_physical_replication_slot('srv_db_02a');.
  4. On the old primary, an empty standby.signal in the data directory and in postgresql.auto.conf a primary_conninfo pointing at 10.20.40.22 with primary_slot_name = 'srv_db_02a'. On start it follows the new timeline and stays as a standby.

In a failover the order changes: the replica is promoted, and the old primary is kept powered off (with its service disabled) until it is rejoined. If it starts and the application writes to it, there are two primaries with different data.

  • In PostgreSQL, the old primary is rejoined with pg_rewind (that is why wal_log_hints = on), which undoes what the standby never received: sudo -u postgres /usr/lib/postgresql/17/bin/pg_rewind --target-pgdata=/var/lib/postgresql/17/main --source-server="host=10.20.40.22 user=postgres dbname=postgres" -R. If it fails, pg_basebackup from scratch.
  • In MySQL, the transactions that only the old primary has show up with GTID_SUBTRACT(<old gtid_executed>, <new gtid_executed>). If it is not empty, it is rebuilt as a replica from a fresh copy, and those transactions are reviewed with the application owner.

5. What the connection string needs

The switch in the database takes a minute; what stretches the outage is having to touch each application's configuration. So that you do not have to:

  • Never a node's IP or name. A service name (db-erp.contoso.local, with a 60-second TTL) that is changed on switchover, a virtual IP or a proxy in front.
  • PostgreSQL allows several servers in the string itself and picking the one that accepts writes. With libpq (psql, Python, Go): postgresql://srv-db-02a.contoso.local,srv-db-02b.contoso.local/erp?target_session_attrs=read-write
  • PostgreSQL from Java (JDBC): jdbc:postgresql://srv-db-02a.contoso.local:5432,srv-db-02b.contoso.local:5432/erp?targetServerType=primary
  • PostgreSQL from .NET (Npgsql): Host=srv-db-02a.contoso.local,srv-db-02b.contoso.local;Database=erp;Target Session Attributes=primary
  • MySQL has no general equivalent in its clients: a service name, a virtual IP or MySQL Router in front. If you want MySQL to handle the switch, InnoDB ReplicaSet (MySQL Shell) builds on this same GTID replication and Router sends writes to the primary.
  • Reconnection: after the change, connections open against the old primary fail (ERROR 1290 ... --super-read-only in MySQL, cannot execute INSERT in a read-only transaction in PostgreSQL). The connection pool must validate a connection before using it and discard broken ones. Java applications cache DNS: networkaddress.cache.ttl at 60 seconds.

6. The ticket: "reports from the replica show yesterday's data" and "the replica has stopped"

Thursday, 9:30. Accounting says the reports, which run against the replica, show nothing recorded this morning.

Case 1: the replica is hours behind (MySQL). Both threads on Yes, Seconds_Behind_Source: 18240 (5 hours) and Retrieved_Gtid_Set well ahead of Executed_Gtid_Set: the replica receives but does not apply fast enough. What it is applying:

A single transaction since 3:00: the nightly purge job deleted 40 million rows from log_auditoria with a single DELETE. With row-based replication the replica deletes row by row, and if the table has no primary key, each row is a full table scan. The tables without a primary key:

  • Now: if the estimate of what remains is hours, wait and tell Accounting that today's reports run against the primary or later in the afternoon. If it is days, rebuild the replica (step 1).
  • So it does not happen again: a primary key on the table (a change for the application team), the purge in batches (DELETE ... LIMIT 10000 in a loop) and sql_require_primary_key = ON so no more tables like that are created. Multiple applier threads (replica_parallel_workers, 4 by default) do not help with a single giant transaction.

The same symptom in PostgreSQL: replay_lag of hours with low write_lag and flush_lag. The standby receives the WAL but does not apply it because a long reporting query blocks it. On the standby, pg_stat_activity shows the hours-long query and postgresql.auto.conf a max_standby_streaming_delay = -1 that someone set so reports would not be cancelled: the standby waits for the query indefinitely. Set it back to 30 seconds (the default) or move reports to a dedicated standby.

Case 2: the replica has stopped with an error. After nine days powered off for a storage array change:

The primary has already deleted the binary logs the replica needs (they are kept for 7 days). There is no fix on the replica: it is rebuilt with a fresh seed (step 1). In PostgreSQL, the equivalent shows up in the standby's log:

It happens without a slot, or when the slot exceeded max_slot_wal_keep_size and went lost. Fix: pg_basebackup again (step 2).

In the ticket: which replica, exact lag or error, cause (the transaction, the query, the days stopped), what was done and the alert that was missing from monitoring.

Next steps

  • Rehearse the planned switchover twice a year, with the real application and measuring how long the outage lasts.
  • Add lag, threads, the slot and the age of the oldest binary log versus the longest a replica may be stopped to monitoring.
  • For automatic failover: Patroni for PostgreSQL or InnoDB Cluster for MySQL. Neither replaces knowing how to do this guide by hand.
