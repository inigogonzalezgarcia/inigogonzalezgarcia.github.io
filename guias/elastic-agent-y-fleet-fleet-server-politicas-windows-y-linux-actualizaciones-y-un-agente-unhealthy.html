Elastic Agent and Fleet: Fleet Server, agent policies, Windows and Linux integrations, enrolling and upgrading agents, and a Windows server that is Unhealthy or sends no data

Replacing standalone Filebeat and Winlogbeat with Elastic Agent managed from Kibana: Fleet Server and its ports, one policy per server type, the System and Windows integrations (with Sysmon as an option) and the Linux ones, enrolment with a token from the command line or an MSI, upgrades in batches, what Beats are still for, and what to do with an Unhealthy agent or a Windows server that sends nothing.

Level 3 · Elasticsearch, Logstash and Kibana · 10 min read · Updated 6 Nov 2026

Rather practise it?Solve the simulated ticket "Elastic Agent: 15 computers offline in Fleet" in SysAdmin Desks ↗

What you'll get

Logs and metrics from every server reaching Elasticsearch with a single agent per machine whose configuration is changed from Kibana, without logging on to each server to edit a YAML file. One Fleet Server, one policy for Windows and another for Linux, a new server enrolled with one command, upgrades of hundreds of agents in batches, and how to diagnose an agent that shows Unhealthy or a server that sends nothing.

Before you start

  • Elasticsearch and Kibana 9.x (or a recent 8.x) with security and TLS enabled, signed by the internal CA. The stack with Filebeat and Logstash is in the centralize logs with ELK guide, and data streams and retention in the Kibana, alerts and ILM one.
  • A Linux server for Fleet Server (srv-fleet-01, 10.20.50.15, 2 vCPUs and 4 GB are enough for a few hundred agents) with the name fleet.contoso.local in DNS and a certificate from the internal CA for that name.
  • The ports, which is where half of all deployments fail:

1. What changes compared with Beats

  • Elastic Agent is a single service per machine. Inside it still uses the Beats components, but it is not configured by hand: it receives a policy from Fleet (the part of Kibana that manages agents).
  • An integration is a package with the collection settings, the ingest pipelines that split out the fields, the data stream templates and the Kibana dashboards. Data lands in data streams named logs-<dataset>-<namespace>, such as logs-system.security-default or logs-windows.sysmon_operational-madrid.
  • The policy's namespace (default, madrid, produccion) is the last part of the name: it is how you separate permissions and retention by site or environment.

What Beats are still for. Filebeat, Metricbeat and the rest are still supported in 9.x. They make sense where they already work and there is no reason to touch them, or where you do not want to depend on Fleet. For the latter there is also Elastic Agent in standalone mode, with a local elastic-agent.yml. For new servers, Elastic Agent with Fleet. Winlogbeat is replaced by the Windows integration.

2. Fleet Server

In Kibana, Management › Fleet › Settings:

  • The CA fingerprint (SHA-256 of the CA certificate, without the colons) makes every agent trust Elasticsearch without copying the CA file to each machine: openssl x509 -fingerprint -sha256 -noout -in ca-contoso.pem.
  • If the servers have no internet access, Agent binary download points to an internal mirror with the packages from artifacts.elastic.co.

Then, Fleet › Agents › Add Fleet Server › Advanced: it creates the Fleet Server Policy, generates a service token and shows the command. On srv-fleet-01:

  • Fleet Server is itself an Elastic Agent with the Fleet Server integration: it appears in the agent list like any other.
  • So it is not a single point of failure, a second Fleet Server (srv-fleet-02) with the same policy, and fleet.contoso.local in front of both (a load balancer or two URLs in Fleet Server hosts).

4. The Windows and Linux integrations

Windows, two integrations in the same policy:

  • System: the Application, System and Security Event Viewer logs, and CPU, memory, disk, network and process metrics.
  • Windows: PowerShell and PowerShell Operational (what the PowerShell logging policy from the security GPOs guide starts producing), Forwarded if the server collects forwarded events, service metrics and performance counters (perfmon), and Sysmon Operational.

Sysmon, from Sysinternals, records process creation, network connections and registry changes in much more detail than the Event Viewer. It is optional and installed separately, with a configuration file that filters out the noise:

The Windows integration's Sysmon Operational channel is only turned on in the policy for servers that have it (win-servidores-sysmon). Asking for a channel that does not exist leaves the agent in a bad state (section 6).

Linux, the System integration reads /var/log/auth.log and /var/log/syslog on Ubuntu, /var/log/secure and /var/log/messages on RHEL, and collects the same metrics. If the distribution does not write those files (journald only), the Custom Journald logs integration. And the integration for the service running on the machine: Nginx, Apache, MySQL or PostgreSQL come with ready-made dashboards.

Domain controllers' Security logs take up the most space. Before turning them on, a dedicated ILM policy for logs-system.security-* with the retention audit asks for.

5. Enrolling and upgrading agents

Each policy has its own enrollment token (Fleet › Enrollment tokens). The token decides which policy the agent joins.

  • It installs to C:\Program Files\Elastic\Agent (on Linux, /opt/Elastic/Agent) and runs as a service under the system account, which is the one that can read the Security log.
  • To deploy to many machines, the MSI with the same parameters: msiexec /i elastic-agent-9.2.1-windows-x86_64.msi INSTALLARGS="--url=https://fleet.contoso.local:8220 --enrollment-token=...", from GPO, MECM or Intune.
  • On Linux with the .deb or .rpm package, installing does not enrol: sudo elastic-agent enroll --url=https://fleet.contoso.local:8220 --enrollment-token=... and then sudo systemctl enable --now elastic-agent.
  • The internal CA must be in the system store (on Windows, the computer's Trusted Root Certification Authorities, by GPO) or be given with --certificate-authorities.

Upgrade, in this order: Elasticsearch, Kibana, Fleet Server and, last, the agents. An agent cannot be ahead of Fleet Server.

  • Rolling upgrade spreads the upgrades over the chosen time so 212 packages are not downloaded at once.
  • First a test policy with five non-critical servers; the next day, the rest.
  • If an agent does not start properly after upgrading, it rolls back to the previous version by itself and Fleet flags it with the upgrade error.

6. The ticket: "srv-file-03 shows Unhealthy in Fleet and Kibana has no logs from it since yesterday"

Thursday, 9:10. In Fleet › Agents, srv-file-03 shows Unhealthy, and Discover has no events from it since 17:00 yesterday.

The states Fleet shows:

StateWhat it means
HealthyConnects to Fleet Server and all its inputs work
UnhealthyConnects, but an input or the output is failing
OfflineHas not connected to Fleet Server for a few minutes: service stopped, machine off, network
UpdatingApplying a policy or an upgrade
InactiveOffline for so long it passed the policy's inactivity timeout
  1. Which part fails: in Kibana, the agent › Agent details, each integration with its state. On the server itself, the same in more detail:

Cause 1, the Sysmon channel. Yesterday someone turned on Sysmon Operational in win-servidores, and srv-file-03 does not have Sysmon. Turn the channel off in that policy (the servers with Sysmon already have their own) or install Sysmon on the server. The agent returns to Healthy within a minute.

  1. If the agent is Healthy but no data arrives, the problem is the output: the agent talks to Fleet Server on 8220, but data goes over 9200 to Elasticsearch. The agent's logs say so:

Cause 2, the port. The server was moved yesterday to the file servers VLAN and the firewall rule only allows 8220. Open 9200 towards the Elasticsearch nodes. If the error were x509: certificate signed by unknown authority, the port is fine and the CA fingerprint is missing from the output (step 2) or the CA from the machine.

  1. If it shows Offline: Get-Service "Elastic Agent", the machine's time (with the clock skewed, TLS fails) and Test-NetConnection fleet.contoso.local -Port 8220.
  1. When it is not clear, the diagnostics bundle: elastic-agent diagnostics on the server, or Request diagnostics .zip on the agent's page in Fleet. It contains the full policy and every component's logs.

The diagnostics bundle may contain unredacted credentials. Treat it as sensitive: do not attach it to a ticket everyone can read or send it by email.

In the ticket: agent, state, failing component and exact message, cause (the policy change or the firewall rule), fix and the check in Discover that events are arriving again.

Next steps

  • A Kibana alert rule for agents that go Unhealthy or Offline for more than 15 minutes, and another for servers with no events in the last hour.
  • Elastic Defend is added to the same policy as one more integration: endpoint protection and detection with the agent that is already installed.
  • Review the retention of the new data streams in the Kibana and ILM guide: Security and Sysmon logs fill disks fast.
