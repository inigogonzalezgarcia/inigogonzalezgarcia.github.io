Guides · Level 3

Running Zabbix: escalating actions and remote commands, Microsoft Teams, maintenance by tags and by API, user groups with Active Directory, housekeeping and database size, and an alert storm after a WAN outage

The day-to-day of a Zabbix that already works: escalations with an automatic restart before anyone is called, alerts to a Teams channel through Workflows, maintenance that only silences what it touches and that the patch script opens itself, sign-in with Active Directory accounts over LDAP, a database that does not grow unchecked, and the storm of 120 alerts when a branch WAN goes down.

Level 3 · Zabbix: server, agents and templates · 12 min read · Updated 6 Nov 2026

What you'll get

A Zabbix that several people can run without it turning into noise: alerts reach the team's Teams channel, a stopped service is restarted automatically before anyone is woken up, patching opens its own maintenance, every engineer signs in with their domain account and sees only their part, the database has a predictable size and a branch outage produces one alert, not a hundred and twenty.

Before you start

  • Zabbix 7.0 LTS with the email, basic actions and maintenance from the server, agent 2 and templates guide. This guide starts from there.
  • A Teams team with a channel for alerts (Monitoring) and a Microsoft 365 licensed account that can create flows in Workflows. The free Teams plan does not include Workflows.
  • In Active Directory, a service account for the LDAP lookup (svc-zabbix-ldap) and security groups for each profile (GG-Zabbix-Admins, GG-Zabbix-Systems, GG-Zabbix-Network).
  • Access to the Zabbix server's database and a recent backup before touching housekeeping or installing TimescaleDB.

1. Escalating actions: the automatic fix first

The action, in Alerts › Actions › Trigger actions:

  • Steps: step 1 runs when the problem opens; step 2, ten minutes later if it is still open; 3-0 means from step 3 onwards, repeating every 30 minutes until it is resolved or someone acknowledges it.
  • If the restart fixes the service, the problem closes before step 2 and nobody receives anything. Reports › Action log records the command and its result.
  • Update operations tells whoever already received the problem when someone acknowledges it, changes the severity or adds a comment: on-call knows someone else has it.
  • Conditions on a tag (service:erp) are more stable than on a host group: a new server with the tag joins the action on its own.

A remote command on a service that crashes because of an application error restarts it in a loop every time it fires. Limit it to services with a known, documented failure, and let step 2 alert anyway if the problem persists.

2. Alerts to Microsoft Teams with Workflows

Microsoft has retired the Office 365 connectors (Incoming Webhook) that the old MS Teams media type relied on. The one to use now is MS Teams Workflow, which posts to a Workflows flow:

  1. In Teams, Workflows › New flow with the Post to a channel when a webhook request is received template. Name Zabbix, the team and the Monitoring channel, Create flow. Copy the flow URL.
  2. In Administration › Macros, the global macro {$ZABBIX.URL} = https://zabbix.contoso.local/zabbix/: messages carry links to the problem.
  3. In Alerts › Media types, the MS Teams Workflow type. If your 7.0 release does not include it, import the media_msteams_workflow.yaml file from the Zabbix repository with Import.
  4. A service user in Zabbix (teams-systems) with an MS Teams Workflow media and the flow URL in Send to, and with read permission on the host groups it should see. The action sends to that user.
  • The flow URL is a credential: whoever has it can post to the channel. It goes in the service user's media, not in an email.
  • One channel per team (Systems, Network) and the severity on each service user's media: High and Disaster to the channel, everything else only on the dashboard.
  • The flow is created with a person's account. If that person leaves the company, the flow stops working: better a licensed service account, or a flow owned by several team members.

3. Maintenance by tags and from the patch script

The previous guide creates a maintenance period by hand for patch night. Two improvements:

Silence only what you touch. A maintenance period with tags suppresses only problems with that tag; everything else on the host keeps alerting:

During that hour, the web-site-down problem is suppressed, but a full disk on the same server alerts as usual.

A single problem: in Monitoring › Problems, Update on the problem and Suppress until a date, with a comment. For the disk that will be extended on Thursday, without creating a maintenance period.

Let the patch script create the maintenance: with an API token (in Users › API tokens, belonging to a service user with write permission only on the groups it patches), the same script that reboots servers opens the window:

  • period is in seconds (3 hours). The server checks maintenance periods every minute: the script waits a couple of minutes before the first reboot.
  • At the end, maintenance.delete with the returned id, so the maintenance does not stay open if patching finishes early.
  • The token, in an environment variable or in the secret store of the system that runs the script, never written into the script.

4. User groups, roles and Active Directory sign-in

In Zabbix 7.0 access is made of two pieces:

  • The role (Users › User roles): which interface sections a user sees and what they can do (acknowledge, close problems, run scripts). Types User, Admin and Super admin.
  • The user group (Users › User groups): which host groups they have read, read-write or no permission on.

GG-Zabbix-AdminsZabbix administratorsSuper admin roleEverything

GG-Zabbix-NetworkNetworkAdmin roleRead-write on Network/, read on Servers/
GG-Zabbix-ServiceDeskService DeskUser roleRead on everything, no scripts

The directory link, in Users › Authentication › LDAP settings, with automatic provisioning (JIT): the user is created in Zabbix the first time they sign in, in the group and with the role of their AD group:

  • On the Authentication tab, Deprovisioned users group set to a disabled group: whoever leaves the AD groups loses access at the next provisioning run (Provisioning period).
  • Test with a real user before saving. The most common failure is the LDAPS certificate: the Zabbix server must trust the CA that issued the domain controllers' certificate.
  • The internal Admin account stays as the emergency account, in a group with Frontend access: Internal, with its password in the team's password manager. If AD does not answer, it is the only way in.
  • If sign-in already goes through SAML with Entra ID or Keycloak, Zabbix 7.0 also supports SAML with provisioning; the group and role logic is the same. The Keycloak guide explains the provider side.

5. Housekeeping and database size

Zabbix stores two things: history (every collected value) and trends (hourly minimum, average and maximum). History is what grows. First, measure:

  • Cut history where it adds nothing: traffic on every switch port does not need 31 days of per-minute values; with 7 days of history and a year of trends, long graphs look the same. Change it on your own template or on the item prototype, not on the official one.
  • A large history_log is usually a log item not filtered on the agent (the Windows and Linux in depth guide explains how to filter at the source).
  • Administration › Housekeeping sets how long events, problems, sessions and history are kept. Override item history period applies a single period to everything and ignores what each item says.
  • The housekeeper deletes row by row every hour (HousekeepingFrequency=1, MaxHousekeeperDelete=5000 in zabbix_server.conf). With large databases it cannot keep up: it shows in the server log (housekeeper [deleted ... hist/trends ... in ... sec]) with times in minutes.

With PostgreSQL, TimescaleDB: it stores history in time chunks, drops whole chunks instead of rows and compresses old ones. With the Zabbix server stopped and a backup taken:

  • The TimescaleDB package and shared_preload_libraries = 'timescaledb' in postgresql.conf must be in place first. Check that the TimescaleDB version is among those supported by your 7.0.x in the release notes.
  • Administration › Housekeeping then shows Enable compression and Compress records older than (7 days by default). With weeks of history, compression cuts the space several times over.
  • Migrating a large database takes time: it is done in a change window, with the backup tested.

With MySQL, the usual alternative is to partition the history and trends tables by day or month with a script or stored procedure. It is not part of Zabbix: if you do it, disable history and trends housekeeping in Administration › Housekeeping so they do not compete, and document who maintains the script.

6. The ticket: "120 alerts in Teams when Valencia went down"

Wednesday, 10:05. The Valencia branch WAN goes down for 40 minutes due to a carrier fault. 124 messages arrive in the Teams channel in a quarter of an hour and the Madrid on-call takes a while to see there is only one fault. At 10:45 the line comes back and as many recovery messages arrive.

  1. The first on the list: Monitoring › Problems, filtered by Valencia and sorted by time. The first is RT-VALENCIA-01: Unavailable by ICMP ping at 10:05:20, checked from the central server. The rest, in the following two minutes.
  2. Where the rest come from: almost all are Valencia hosts with Monitored by: Server, created before the branch proxy existed, plus some web checks from Madrid against Valencia applications. The hosts already going through PRX-VALENCIA generated nothing: the proxy kept collecting, stored the data and sent it when the line came back.
  3. In the moment: mark the router's problem as the cause and the rest as symptoms (Monitoring › Problems, select, Mark as cause and Mark selected as symptoms). With Pause operations for symptom problems on the action, the symptoms stop escalating; only the router problem continues, and it is acknowledged with the carrier's fault number.
  4. So it does not happen again:
  • Every Valencia host moves to Monitored by: Proxy › PRX-VALENCIA. Local things are measured locally.
  • From the central server, only the branch as a whole is watched: the router and the proxy (zabbix[proxy,"PRX-VALENCIA",lastaccess]). The proxy trigger depends on the router trigger.
  • Web checks from Madrid towards Valencia depend on the router trigger.
  • The Teams action sends only High and Disaster; the branch's Warning problems stay on the dashboard.
  1. Check at the next outage or with a controlled test (bring the tunnel down in an agreed window): one router-down message, one proxy-not-in-contact suppressed by dependency, and nothing else.

In the ticket: the number of messages before and after, the list of hosts moved to the proxy, the dependencies added and the test result.

The general rule: each branch has one "the branch is not answering" alert, and everything behind it depends on it. A WAN outage is one problem, not a hundred and twenty.
