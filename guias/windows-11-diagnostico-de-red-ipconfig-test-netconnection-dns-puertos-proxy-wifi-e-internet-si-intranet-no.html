Windows 11: network diagnosis for the service desk with ipconfig, Test-NetConnection, DNS, ports, proxy, the Wi-Fi report and "internet works, the intranet doesn't"

The PowerShell and cmd commands that solve most network tickets: ipconfig /all, Test-NetConnection for ping, ports and trace, Resolve-DnsName and the DNS cache, which process uses a port, the WinHTTP and user proxy, the Wi-Fi report, and the laptop where internet works but the intranet does not.

Level 1 · Windows 10 and 11 · 9 min read · Updated 6 Nov 2026

What you'll get

Knowing in five minutes which layer a workstation's network problem is in: whether the computer has a good address, whether it reaches the server, whether the name resolves, whether the port answers, whether there is a proxy in the way or whether it is the Wi-Fi. With that, you either fix it or escalate it to the network team with data, not with "the internet is down".

Before you start

  • PowerShell on the user's computer (remotely, with the company's remote support tool). Almost everything works without admin rights; the Wi-Fi report and some netstat details do need them.
  • The computer name, whether it is in the office, at home or on VPN, and what exactly is not working: a website, an app, a drive, everything.
  • The address of the failing service: intranet.contoso.local, srv-app01, a port if you know it.

The order is always the same, bottom up: IP address, gateway, DNS, port, proxy. Jumping to the end ("it'll be the proxy") wastes more time than it saves.

1. ipconfig /all: which network the computer is on

What you look at, in this order:

  • IPv4 Address: a 169.254.x.x means it got no IP from DHCP (the DNS and DHCP guide follows that case from the server). A 192.168.1.x on a laptop that claims to be in the office: it is on another network.
  • Default Gateway: without it, nothing outside its subnet.
  • DNS Servers: in the office, the domain controllers. An 8.8.8.8 or the home router on a computer that needs the intranet is already a clue.
  • DNS suffix and search list: what gets added to a short name such as intranet. If empty, only full names work.
  • With a VPN connected, another adapter appears with its own IP and DNS servers.

The shorter PowerShell version: Get-NetIPConfiguration.

2. Test-NetConnection: ping, port and trace

Test-NetConnection (alias tnc) replaces ping, telnet for testing ports and tracert:

  • A failed ping is not a server down: many servers and firewalls block ICMP. The test that counts is the service port: 443 for a website, 445 for a network drive, 3389 for Remote Desktop, 1433 for SQL Server.
  • TcpTestSucceeded : False with a working ping: the server is there, but the service is not listening or a firewall blocks that port.
  • The trace shows how far it gets. If it stops at the gateway, the problem is beyond the workstation.

3. DNS: Resolve-DnsName and the cache

  • -Server asks a specific DNS server. If it resolves with it and not without it, the problem is which DNS the computer asks, not the record.
  • Windows also caches negative answers: after fixing a record, Clear-DnsClientCache (or ipconfig /flushdns) so you do not have to wait.
  • The C:\Windows\System32\drivers\etc\hosts file comes before DNS. A forgotten line from a test sends the name to an old IP: Get-Content C:\Windows\System32\drivers\etc\hosts | Select-String -NotMatch '^#'.
  • nslookup goes straight to the DNS server and skips the cache and the hosts file. To see what the computer really sees, Resolve-DnsName.

4. Which process uses a port

When an app says "port 8080 is in use" or you want to know who a program is talking to:

netstat -ano is the same in cmd: the last column is the PID. netstat -b shows the executable name, but needs an elevated console.

5. The proxy: WinHTTP and the user's

Windows has two proxy settings, and tickets come from mixing them up:

Who uses itHow to see it
User proxy (WinINET)Edge, Chrome, Office, Teams and most user programsSettings › Network & internet › Proxy
WinHTTPSystem services: Windows Update, antivirus, inventory or backup agentsnetsh winhttp show proxy
  • The browser works and Windows Update or an agent does not: the user proxy is fine and WinHTTP does not have it. Set it with netsh winhttp set proxy proxy-server="proxy.contoso.local:8080" bypass-list="*.contoso.local;<local>" (as administrator) or leave it direct if the network allows; netsh winhttp reset proxy removes it.
  • An internal website that returns a proxy error (403, denied by policy): the PAC does not exclude that name and the request goes to the proxy instead of direct. The PAC by GPO is in the Chrome and Firefox by GPO guide.

6. Wi-Fi: the interface and the report

  • Signal below 50% and low rates: the user is far from the access point or behind a wall. The BSSID tells you exactly which access point it is connected to, the detail the network team needs.
  • For drops that "happen now and then", the Wi-Fi report for the last three days. In an elevated console:

It opens in the browser: a chart with each Wi-Fi session, disconnections marked and, for each one, the reason (the computer went to sleep, the access point disconnected, authentication failure). If the drops match sleep, it is power, not the Wi-Fi.

7. The ticket: "internet works, but the intranet doesn't"

Monday, 9:15. Carlos Vidal, working from home with the VPN connected. Outside websites load; https://intranet gives This site can't be reached and the network drive does not open either.

  1. Is it the name or the network? A test by IP, taken from a colleague or from DNS:

The network gets through (the port answers by IP) and the company DNS knows the name. What fails is which DNS the laptop asks.

  1. Which DNS it uses and for what: ipconfig /all shows the VPN adapter with DNS 10.0.10.10 but no suffix, and the home Wi-Fi with the router 192.168.1.1. Windows asks first through the adapter with the lowest metric, and that is the Wi-Fi:

Get-DnsClientNrptPolicy is empty: there is no split DNS rule sending contoso.local to the VPN's DNS servers. With Always On VPN that rule lives in the profile; with other clients, in the concentrator configuration (the split DNS domain list). And without a suffix, the short name intranet is not completed to intranet.contoso.local.

  1. The fix: it is configuration, not the workstation. Escalate to whoever manages the VPN with the evidence: the profile must push contoso.local as a split DNS domain and as a search suffix. As a temporary workaround for the user, reconnecting the VPN after Clear-DnsClientCache is not enough; neither is typing full names, because the full name also goes to the router. In the office, the search suffix comes through DHCP (option 015) or GPO (Administrative Templates › Network › DNS Client › DNS Suffix Search List).
  1. Other causes of the same symptom, in case the first does not fit:
  • The VPN connects but does not publish the route to 10.0.20.0/24: Test-NetConnection 10.0.20.30 -Port 443 fails by IP. It is the network, not DNS (the AnyConnect guide follows that case).
  • The name resolves fine but the browser sends it to the proxy: the PAC does not exclude contoso.local (section 5).
  • An old line in the hosts file with the IP of a previous intranet.

In the ticket: what resolves and what does not (with and without -Server), the port test by IP, the adapter metrics and that the VPN is missing the split DNS rule.
