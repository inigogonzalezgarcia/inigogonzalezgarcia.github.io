Zabbix: hardware and power, with iDRAC and iLO over SNMP, IPMI and Redfish, the APC UPS, VMware ESXi and vCenter, a branch proxy and a proxy that stops sending data

What sits under the servers in Zabbix 7.0: Dell iDRAC and HPE iLO controllers with SNMP or Redfish templates and IPMI, the APC UPS with battery, runtime and battery replacement, vCenter and ESXi with the VMware collectors, a PSK proxy for the Valencia branch and what to check when the proxy stops sending data.

Level 3 · Zabbix: server, agents and templates · 10 min read · Updated 6 Nov 2026

What you'll get

Hearing from Zabbix about what the operating system agent cannot see: a failed disk or power supply in a physical server, the UPS that has gone to battery or is asking for new batteries, the VMware datastore filling up and an ESXi host that disconnects. At the branch, a proxy that collects all of that locally and sends it encrypted to the central server. And, when the branch stops having recent data, knowing where the chain is broken.

Before you start

  • Zabbix 7.0 LTS with the server from the server, agent 2 and templates guide.
  • The controllers with an IP on the management VLAN and SNMP or a read-only user configured on them: the controller side is in iDRAC and iLO: out-of-band management. The UPS network card, in APC UPS: network card and alerts.
  • Ports from the server or proxy: 161/UDP (SNMP), 443/TCP (Redfish and vCenter), 623/UDP (IPMI). From the proxy to the central server, 10051/TCP.
  • A read-only vCenter account for Zabbix, and a small VM at the branch (2 vCPU, 2 GB) with Ubuntu 24.04 for the proxy.

1. iDRAC and iLO over SNMP

The simplest way: the controller answers SNMP and Zabbix creates it as one more host, with its management IP.

ControllerSNMP template in 7.0Redfish (HTTP) template in 7.0
Dell iDRAC 7, 8 and 9DELL PowerEdge R7xx by SNMP (R720, R740, R750, R820, R840)DELL PowerEdge R7xx by HTTP (iDRAC 8 and 9)
HPE iLO 4, 5 and 6HP iLO by SNMPHPE iLO by HTTP
  • The Dell templates carry a model in their name, but they read the iDRAC MIB, common to the generation: the closest model's template works for the rest. Check in Latest data that disks, power supplies and fans come through.
  • What they bring: overall status, power supplies, fans, temperatures, physical and virtual disks on the RAID controller, and alerts when the firmware or serial number changes.
  • One host per controller, separate from the operating system host. If the server hangs, the controller keeps answering; if the controller stops answering, the server may still be fine.

2. Redfish and IPMI

Redfish is the REST API of current controllers. The by HTTP templates run the queries from the server or proxy with a controller user:

  • On the iDRAC or iLO, a local user zbx-monitor with a read-only role (Read Only on iDRAC, Login with no further privileges on iLO). Never the administrator account.
  • On the Zabbix host, the template and its URL, user and password macros; the password as Secret text. The host needs no SNMP interface.
  • Redfish or SNMP, not both on the same controller: they duplicate alerts, and the iDRAC answers more slowly if it is asked about everything twice.

IPMI is kept for old devices or other vendors. The server (or proxy) needs IPMI pollers, which default to 0:

On the host: an IPMI interface with the controller's IP and port 623, and on the IPMI tab the user, password and Privilege level User. The Chassis by IPMI template discovers the sensors. On the iDRAC, IPMI over LAN is disabled by default: racadm set iDRAC.IPMILan.Enable 1.

IPMI 2.0 has known weaknesses in its authentication. Only on the management VLAN, reachable from the Zabbix server or proxy, and disabled on controllers where Redfish or SNMP already cover the same.

3. The APC UPS over SNMP

With the UPS network card answering SNMP, the APC UPS by SNMP template brings what is needed:

Template triggerSeverityWhat it means
UPS is on batteryAverageMains power has failed
Battery is LowAverageLittle battery left: shutdown is close
Battery has low capacityHighCharge below {$BATTERY.CAPACITY.MIN.WARN} (50 %)
Battery needs replacementHighThe self-test failed: order batteries
Output load is highHighLoad above {$UPS.OUTPUT.MAX.WARN} (80 %)
Unacceptable input voltageHighInput voltage outside 197-243 V

The template has the remaining runtime item but no trigger on it. It is the figure that decides whether to start shutting down, so add one of your own in a linked template:

  • 10m in an expression equals 600 seconds: Zabbix understands time suffixes.
  • UPS is on battery with an immediate action, on a stormy day, produces 20-second alerts. The action can wait 2 minutes on the first step; the runtime trigger cannot.
  • The servers that depend on the UPS: their "unavailable" triggers depend on the runtime one, so that after an orderly shutdown one alert arrives and not twenty.

4. VMware: vCenter, ESXi hosts and datastores

Zabbix queries the vCenter API with dedicated processes, the VMware collectors, which are disabled by default:

In vCenter, a user svc-zabbix@vsphere.local (or a domain one) with the Read-only role assigned at the root of the inventory and set to propagate. In Zabbix, a host for the vCenter with no interfaces:

  • The template discovers clusters, datastores, ESXi hosts (with the VMware Hypervisor template) and virtual machines (with VMware Guest) and creates them as hosts. Those templates are not linked by hand.
  • VMware FQDN names VMs by their DNS name and needs VMware Tools and unique names; VMware uses the VM's UUID.
  • If the VMs already run the Zabbix agent, they are duplicated: the agent host and the discovered host. Keep VM discovery only for those without an agent, or disable that prototype and keep hosts and datastores.
  • The most useful parts: free space on each datastore, disconnected hosts or hosts in maintenance, vCenter alarms, and CPU and memory per host. The vSphere side (maintenance, snapshots) is in vSphere and vCenter.
  • The internal item zabbix[vmware,buffer,pused] tells you if the cache is too small: above 80 %, raise VMwareCacheSize.

5. A proxy for the branch

The Valencia branch has its own servers, UPS, switches and a WAN line to Madrid. An active proxy at the branch runs every query there and sends the results to the central server on 10051, encrypted with PSK. Installing the package and the offline buffer are covered in the Zabbix for hospitality guide; here, what a corporate branch adds:

On the central server, Administration › Proxies › Create proxy:

  • The file's Hostname and the Proxy name identical, case included. Proxy address limits which IP that proxy is accepted from.
  • The branch hosts move to Monitored by: Proxy › PRX-VALENCIA. Their agents have Server and ServerActive pointing to the proxy, and the branch SNMP ACLs, the proxy's IP.
  • The proxy watches itself: a host prx-valencia monitored by the proxy itself, with agent 2 and the Zabbix proxy health template, which alerts on queues, full caches and busy processes.
  • In 7.0, several proxies can form a proxy group (Administration › Proxy groups) that shares out the hosts and covers if one fails. A branch with a single proxy does not need it.

6. The ticket: "Valencia has had no data for hours"

Monday, 8:15. On the dashboards, the Valencia servers' graphs have been flat since Saturday at 22:40. No host-down alert has arrived: nodata() triggers for hosts behind a proxy do not fire while the proxy is not connecting, precisely so as not to produce a hundred alerts for a single cause.

  1. The proxy, as the server sees it: in Administration › Proxies, PRX-VALENCIA shows a Last seen (age) of 33h and state Offline. The problem is between the proxy and the server, not on the hosts.
  2. The proxy log, in /var/log/zabbix/zabbix_proxy.log. The message says which part fails:
Message in the proxy logUsual cause
cannot connect to [[zabbix.contoso.local]:10051]Network or firewall: the WAN, the tunnel or a rule for 10051
proxy "PRX-VALENCIA" not foundThe name does not match the frontend's, or the proxy was deleted and recreated
TLS or PSK errorsDifferent identity or key in the file and in the frontend
database or disk is fullThe proxy disk is full (the SQLite database or the log)
  1. The cause: the Madrid firewall was migrated on Saturday at 22:30 and the rule allowing 10051 from 10.20.0.5 to the server was not carried over. The tunnel works; only that port is missing.
  2. Fix and recovery: with the rule restored, the proxy reconnects within seconds and starts sending what it has stored. With ProxyOfflineBuffer=24, the last 24 hours are kept; the first 9 hours of the outage are lost. Administration › Queue shows the proxy's queue going down as the buffer empties.
  3. Check: Last seen (age) in seconds, Latest data for a Valencia server with values from the last few minutes, and the graphs filled in from Sunday.
  4. So next time it is known in minutes, not days: a trigger on the central server on zabbix[proxy,"PRX-VALENCIA",lastaccess], like the one in the hospitality guide, with High severity and in the network on-call action. And the buffer, sized to how long the team really takes to notice: 72 hours cover a weekend if the disk allows it.

If the central server has just been upgraded to another major version and the proxy has not, Administration › Proxies shows its version flagged as outdated: an older proxy may stop receiving configuration. Server and proxies are upgraded in the same window.

In the ticket: the proxy's Last seen, the log message, the missing rule, the hours of data lost and the new trigger.
