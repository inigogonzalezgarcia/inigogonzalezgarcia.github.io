Active Directory: password and lockout policy, PSOs for admins and service accounts, and the account that locks itself every morning

The domain password and lockout policy, fine-grained policies (PSOs) for admins and service accounts, reading the effective one with Get-ADUserResultantPasswordPolicy, event 4740 on the PDC emulator, Account Lockout Status, and the account that locks every morning because of a drive, a phone or an old credential.

Level 1 · Active Directory: users and groups · 9 min read · Updated 6 Nov 2026

Rather practise it?Solve the simulated ticket "The account that locks every morning" in SysAdmin Desks ↗

What you'll get

Knowing which password and lockout policy each account has, giving admins and service accounts a different one without touching the rest of the domain and, above all, finding where the failed attempts come from when an account locks itself. Unlocking takes a minute; without finding the source, the ticket comes back tomorrow.

Before you start

  • RSAT installed: Active Directory Users and Computers, Active Directory Administrative Center (ADAC), Group Policy Management (GPMC) and the PowerShell module.
  • To read the domain controllers' Security log: membership of Event Log Readers on the DCs or a delegated admin account.
  • To create fine-grained policies: Domain Admins or delegated permissions on the Password Settings Container. The domain functional level must be 2008 or higher (it is in any current domain).
  • User account management auditing enabled on the DCs: without it there is no event 4740. The guide on delegation, the recycle bin and who changed this user explains how to turn it on.

1. The domain policy: one for everyone

The password and lockout rules for domain accounts live in a GPO linked to the domain root, normally the Default Domain Policy: Computer Configuration › Policies › Windows Settings › Security Settings › Account Policies.

  • Only the one linked to the domain counts. A GPO with a password policy linked to an OU only changes the local accounts of the computers in that OU, not the domain users.
  • The quick way to see what is there:

The three lockout values, the ones that generate tickets:

SettingWhat it doesIn a newly created domain
Account lockout threshold (LockoutThreshold)Failed attempts before locking0: the account never locks
Account lockout duration (LockoutDuration)How long the account stays locked; 0 = until an admin unlocks itNot defined
Reset account lockout counter after (LockoutObservationWindow)Time after which the attempt counter goes back to zeroNot defined

Microsoft's security baselines suggest 10 attempts and 15 minutes for both duration and window. A threshold of 3 floods the desk with tickets and makes it easy to lock anyone out on purpose; a duration of 0 means a call to support every time.

The other defaults of a new domain: 42-day maximum age, 7-character minimum length, history of 24 and complexity enabled. Seven characters is too short: 12 or more for users, and a long password is better than a short expiry.

2. Fine-grained policies (PSOs) for admins and service accounts

A fine-grained password policy (stored as a PSO object) replaces the domain one for the accounts it applies to. Three rules:

  • It applies to users or global security groups, never to an OU.
  • Each PSO has a precedence: if several reach an account, the lowest number wins. A PSO linked directly to the user beats those that come through a group.
  • A PSO is complete: it carries every value, lockout included.

In ADAC: contoso (local) › System › Password Settings Container › New › Password Settings. With PowerShell, one for admin accounts and another for classic service accounts:

  • Admins (adm-): a longer password and stricter lockout, because these are the accounts that get attacked.
  • Service accounts: a very long random password and no lockout, so nobody can take a service down by failing the password on purpose. It is a trade-off: without lockout, length is the protection. Better still, have the service use a gMSA, which has no password to expire or to be mistyped (the gMSA service accounts guide explains it).

A universal or distribution group does not work: the PSO is assigned but not applied. Use global security groups.

3. Which policy an account really has

With PSOs in play, looking at the Default Domain Policy is no longer enough. The resultant policy of an account:

If it returns nothing, that account gets the domain policy. In ADAC, right-click the user › View resultant password settings... shows the same. The password expiry date, already calculated with the PSO, is in the msDS-UserPasswordExpiryTimeComputed attribute (the weekly Active Directory report guide turns it into a date).

4. How a lockout works

  1. The user (or something using their name) fails the password against a DC. Before returning the error, that DC asks the PDC emulator, in case the password has just changed.
  2. Each DC keeps its own badPwdCount counter, which is not replicated; the PDC sees every failure forwarded to it.
  3. When the threshold is reached, the account is locked, the lockout replicates urgently to every DC and the PDC emulator logs event 4740, with the name of the source computer.

5. Finding the source

Event 4740 on the PDC

The event's second field is the Caller Computer Name: the computer that sent the bad password. Three cases:

  • A workstation (PC-0412): the problem is on that computer. Section 6.
  • A server (the on-premises mail server, the NPS for Wi-Fi or VPN, an internal web server): that server only forwards the attempt. The real source is in its own logs: the phone syncing mail, the laptop joining the corporate Wi-Fi with the saved password.
  • Empty: the attempt arrived through a service that does not report the computer. Look on the DCs for event 4771 (Kerberos pre-authentication failed, code 0x18 = wrong password), which carries the client IP address.

Account Lockout Status

LockoutStatus.exe, from Microsoft's Account Lockout and Management Tools package, is an old tool that still works: it asks every DC about one account at once.

6. The ticket: "I get locked out every morning at eight"

Thursday, 8:10. Laura Prado (Sales) changed her password on Monday. Since Tuesday, every morning when she arrives the account is locked; it gets unlocked, she works all day without trouble, and the next day it happens again.

  1. The source: the PDC's 4740 gives PC-0412 on all three mornings, between 8:04 and 8:06. It is her laptop, and the time matches her sign-in.
  2. What the laptop does at startup with an old password. On the device, with the user signed in:

A P: drive that was once mapped with Connect using different credentials and the password saved in Credential Manager. At each sign-in, Windows retries the connection with the old password several times, and that reaches the threshold.

  1. The other usual causes, in case the first one does not fit:
  • A scheduled task or a service running as the user: Get-ScheduledTask | Where-Object { $_.Principal.UserId -like '*lprado*' } and Get-CimInstance Win32_Service | Where-Object StartName -like '*lprado*'.
  • The phone: the mail app or the corporate Wi-Fi with the previous password. The source computer will be the mail server or the NPS; the fix is updating the password on the phone or forgetting the network.
  • A disconnected Remote Desktop session on a server, opened with the previous password: quser /server:srv-app01 and close it with logoff <id> /server:srv-app01.
  1. The fix: delete the saved credential and map the drive again without alternative credentials (a GPO drive beats a manual one: see the network drives by GPO guide).
  1. The check: unlock, ask her to restart and, the next morning, BadLogonCount at 0 on the PDC and no new 4740.

In the ticket: source computer (4740), cause (saved credential for the P: drive), what was deleted and the next-day check.
