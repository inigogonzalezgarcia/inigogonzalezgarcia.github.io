Guides · Level 3

Advanced auditing by GPO: logons, lockouts, accounts, processes with command line, log sizes, forwarding events to a collector, and the event that isn't there

The advanced audit policy that generates the events you actually investigate (logon, lockout, account and group management, process creation with command line, policy changes), logs big enough to keep them, Windows Event Forwarding to a collector your SIEM reads, and why the event you need is not there.

Level 3 · Security GPOs · 9 min read · Updated 6 Nov 2026

What you'll get

Every computer and server in the domain recording what an investigation asks (who signed in and from where, which account was locked, who added someone to a group, which process ran and with which parameters), those events not overwritten within hours, and all of it reaching a central server the SIEM collects from. And knowing what to check when the event you need is not there.

Before you start

  • GPMC and permissions to create and link GPOs on the computer, server and domain controller OUs.
  • The security baseline already in place: the baseline security GPOs guide covers NTLM, LLMNR, SMB signing, LAPS and PowerShell logging. This guide does not repeat them.
  • A Windows Server 2022 or 2025 server for the collector (srv-wec01.contoso.local), with disk for several days of events and your SIEM's agent if there is one.
  • A pilot OU with computers and a couple of servers, as with any security GPO.

1. Advanced auditing, not basic

Windows has two sets of audit policies. The basic one (Local Policies › Audit Policy) has 9 broad categories; the advanced one has more than 50 subcategories and is the one to use. Mixing both gives unpredictable results, so you configure only the advanced one and force it to win:

  • Security Settings › Local Policies › Security Options › Audit: Force audit policy subcategory settings (Windows Vista or later) to override audit policy category settings = Enabled.

The subcategories live in Computer Configuration › Policies › Windows Settings › Security Settings › Advanced Audit Policy Configuration › Audit Policies. A sensible starting point, in a SEC-Audit GPO linked to computers and servers:

Category › subcategoryValueEvents it gives
Logon/Logoff › Audit LogonSuccess and Failure4624, 4625
Logon/Logoff › Audit Account LockoutFailure4625 with status 0xC0000234 on the device where it was attempted
Logon/Logoff › Audit Special LogonSuccess4672 (session with admin privileges)
Account Management › Audit User Account ManagementSuccess and Failure4720, 4722, 4724, 4725, 4726, 4738, 4740
Account Management › Audit Security Group ManagementSuccess4728, 4732, 4756 (added to group)
Detailed Tracking › Audit Process CreationSuccess4688
Policy Change › Audit Audit Policy ChangeSuccess4719
Policy Change › Audit Authentication Policy ChangeSuccess4706, 4713, 4716

On the domain controllers, a separate GPO (SEC-Audit-DC) with the above plus Account Logon › Audit Credential Validation (4776, NTLM) and Audit Kerberos Authentication Service (4768, 4771). Event 4740 (account locked out) is written on the domain controller holding the PDC emulator role, with the name of the computer that caused the lockout.

Process creation without the command line is of little use. In Administrative Templates › System › Audit Process Creation, Include command line in process creation events = Enabled. Event 4688 then carries the Process Command Line field. It can contain passwords someone types into a script: the security log is already restricted, and the SIEM must be too.

The GPO stores advanced auditing in an audit.csv file inside its SYSVOL folder (Machine\Microsoft\Windows NT\Audit\). To check what the device really applies, use auditpol, not the editor:

On a Windows installed in another language, auditpol subcategory names are localised too; auditpol /get /category:* lists them all with their local names.

2. Log size and retention

The Security log ships at 20 MB. On a file server or a domain controller with advanced auditing, that is hours. In Administrative Templates › Windows Components › Event Log Service:

  • Security › Specify the maximum log file size (KB): 196608 (192 MB) on workstations, which is what Microsoft's baseline sets; 1048576 (1 GB) or more on domain controllers and busy servers.
  • Application and System: 32768 KB.
  • Control Event Log behavior when the log file reaches its maximum size = Disabled (overwrite old events). Retaining without automatic backup fills the log and stops new events being written.

The useful question is not "how big is it" but "how far back does it go": if the oldest event is two hours old, the local log is useless for any investigation and everything depends on the collector.

3. The Windows Event Forwarding collector

Windows Event Forwarding (WEF) forwards events to a central server without an agent: it uses WinRM, which is already in Windows. In source-initiated mode, each device asks the collector what to send; new devices join on their own.

On srv-wec01:

The subscription is created in Event Viewer › Subscriptions › Create Subscription:

  • Better one subscription with several queries than many subscriptions: each one is another connection per device.
  • 4624 from every device is a lot of volume; here only type 10 (Remote Desktop) is sent. Network logons on servers can go in a separate subscription for that group.
  • Normal delivers in batches every 15 minutes; Minimize Latency, in about 30 seconds. For SIEM alerts, minimum latency on what is critical.
  • 1102 (security log cleared) is always logged, with no policy: it is in the query because it is the first thing someone covering their tracks does.

4. The source devices, by GPO

In a SEC-WEF-Source GPO linked to the computer and server OUs:

  1. Administrative Templates › Windows Components › Event Forwarding › Configure target Subscription Manager = Enabled, with the value Server=http://srv-wec01.contoso.local:5985/wsman/SubscriptionManager/WEC,Refresh=600.
  2. Security Settings › System Services › Windows Remote Management (WS-Management) = Automatic.
  3. The forwarding service runs as Network Service and by default cannot read the security log. In Preferences › Control Panel Settings › Local Users and Groups, group Event Log Readers (built-in), action Update, member NT AUTHORITY\NETWORK SERVICE. It needs a restart of the device (or the WinRM service) for the token to pick it up.
  4. On the collector, inbound firewall to 5985 from the device networks (the PowerShell remoting and WinRM guide explains the port and authentication).

With HTTP and Kerberos inside the domain, the content is encrypted by WinRM; HTTPS on 5986 is needed for devices outside the domain, with certificates.

On the source, Applications and Services Logs › Microsoft › Windows › Eventlog-ForwardingPlugin › Operational shows 104 (connected to the subscription manager) and 100 (subscription created). Errors reading the security log show up there too.

Also increase Forwarded Events on the collector (wevtutil sl ForwardedEvents /ms:4294967296 for 4 GB). The SIEM agent (Azure Monitor Agent for Sentinel, Splunk Universal Forwarder, Wazuh) reads that log and ships it; the collector is the single point you watch.

5. The ticket: "the event I need is not in the log"

Security wants to know what the user of PC-0377 ran yesterday at 18:40: a Defender alert mentions a powershell.exe launched from Excel. Event Viewer on PC-0377 has no 4688 at all, and neither does the collector.

  1. Is it being audited? auditpol /get /subcategory:"Process Creation" says No Auditing, even though the SEC-Audit GPO shows as applied in gpresult /r.
  2. Basic overrides advanced. In the gpresult /h report, Local Policies › Audit Policy › Audit process tracking comes from an old GPO on the Sales OU, and Audit: Force audit policy subcategory settings... is Disabled in that same GPO. With the option disabled, the basic category wins over all its subcategories.

Fix: remove the basic policy from the old GPO, leave Force audit policy subcategory settings Enabled (in SEC-Audit, with a link order that wins) and check again with auditpol.

If auditpol says Success and the event is still missing, the next suspect is size:

The log only reaches back to 21:17 last night: the size GPO is not applied on that device (it sat in an OU without the link). The 18:40 event was overwritten and only what reached the collector remains. The ticket note records both causes, the GPO change and the check (auditpol with Success, maxSize: 201326592 and a test 4688 seen on the collector).

When an advanced audit setting is removed from a GPO, the device keeps the configuration it had. To leave a subcategory unaudited you configure it explicitly as No Auditing, or clean up with auditpol /clear on the device and apply the GPO again.
