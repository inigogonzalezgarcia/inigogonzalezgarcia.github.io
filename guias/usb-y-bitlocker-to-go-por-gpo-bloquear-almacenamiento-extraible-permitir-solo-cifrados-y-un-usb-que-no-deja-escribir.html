USB and BitLocker To Go by GPO: blocking removable storage, allowing only approved models, requiring encryption to write, the key in AD, the same with Intune, and an approved USB that won't let you write

Denying read or write on removable drives, preventing USB sticks from installing except approved ones by their identifier, requiring BitLocker To Go to write with the recovery key stored in Active Directory, how Intune does the same, and what to check when an approved encrypted USB is still read-only.

Level 1 · BitLocker · 8 min read · Updated 6 Nov 2026

What you'll get

Company data not leaving on just any USB stick: unencrypted removable drives can be read but not written, only approved models install, approved sticks are encrypted with BitLocker To Go and their recovery key sits in Active Directory. And knowing how to solve the typical call: "I have the encrypted USB IT gave me and it won't let me save".

Before you start

  • The BitLocker status and recovery key guide: this one uses the same commands (manage-bde, Get-BitLockerVolume) on the stick instead of the system disk.
  • GPMC and permissions to create and link GPOs on the computer OUs.
  • A written decision on what is allowed: nothing? read yes and write no? write only to company-encrypted sticks? And a group of who can request an approved stick.
  • A couple of sticks of the approved model and any other one for testing.

1. Blocking read or write

The access policies live in Computer Configuration › Policies › Administrative Templates › System › Removable Storage Access:

PolicyEffect
Removable Disks: Deny write accessUSB sticks and drives show and can be read, but nothing is written
Removable Disks: Deny read accessThey do not open
WPD Devices: Deny read / write accessPhones and cameras connected over USB (MTP)
CD and DVD: Deny write accessBurners
All Removable Storage classes: Deny all accessAll of the above at once

The same ones exist under User Configuration, but in a managed environment they are applied to the computer: they do not depend on who signs in.

If you plan to require BitLocker To Go to write (section 3), do not enable Removable Disks: Deny write access: that policy wins and not even encrypted sticks can be written.

2. Only approved models install

Access controls what is done with the drive; device installation decides whether Windows mounts it at all. In System › Device Installation › Device Installation Restrictions:

  1. Apply layered order of evaluation for Allow and Prevent device installation policies across all device match criteria = Enabled. With it, the most specific wins: instance ID > device ID > class > removable.
  2. Prevent installation of devices that match any of these device IDs = Enabled, with USBSTOR\Disk (every USB mass storage stick shares it as a compatible ID).
  3. Allow installation of devices that match any of these device instance IDs = Enabled, with the instance ID of each stick handed out (it includes the serial number).

You get the ID with the stick plugged into an IT computer:

  • Allowing by hardware ID (USBSTOR\DiskKingstonIronKey_VP50____1.00) admits any stick of that model; by instance ID, only the specific units IT handed out. The second means updating the GPO with each handover, but it is what lets you say which sticks exist.
  • The policy applies to new installations. For sticks already installed, tick Also apply to matching devices that are already installed on the prevent policy.
  • External SSDs with UASP may show up as SCSI\Disk... rather than USBSTOR: check their IDs before calling the rule done.
  • When an installation is blocked, the device notifies the user and C:\Windows\INF\setupapi.dev.log records the policy restriction.

3. BitLocker To Go: encrypt to be able to write

In Administrative Templates › Windows Components › BitLocker Drive Encryption:

  • At the root, Provide the unique identifiers for your organization = Enabled, identification field CONTOSO. Every stick encrypted on a company computer carries that mark.

In Removable Data Drives:

  • Control use of BitLocker on removable drives = Enabled, with Allow users to apply BitLocker protection ticked and suspend and decrypt unticked.
  • Deny write access to removable drives not protected by BitLocker = Enabled, with Deny write access to devices configured in another organization ticked: only sticks with the CONTOSO field can be written.
  • Configure use of passwords for removable data drives: password required, with complexity and a minimum of 12 characters.
  • Choose how BitLocker-protected removable drives can be recovered = Enabled: allow the 48-digit recovery password, do not allow the 256-bit recovery key (it is incompatible with the deny write policy), Save BitLocker recovery information to AD DS and Do not enable BitLocker until recovery information is stored to AD DS.
  • Choose drive encryption method and cipher strength: for removable drives, AES-CBC 256-bit, readable on any Windows; XTS-AES only on Windows 10 and later.

With everything applied, an unencrypted stick can be opened but not saved to, and Windows offers to encrypt it. IT encrypts approved sticks before handing them out (right-click › Turn on BitLocker, or):

A stick's recovery information is stored on the AD object of the computer where it was encrypted, not on the user's. When someone forgets the password, the stick's unlock screen shows the key ID; in Active Directory Users and Computers, right-click the domain › Find BitLocker Recovery Password with the first 8 characters of that ID.

4. If the devices are in Intune

The same exists in Intune, in the admin center:

  • Endpoint security › Disk encryption › BitLocker: Deny write access to removable drives not protected by BitLocker and the removable drive encryption method.
  • Devices › Configuration › Settings catalog: the same Administrative Templates › System › Removable Storage Access and Device Installation Restrictions from sections 1 and 2, with the same IDs.
  • Endpoint security › Attack surface reduction › Device control: with Microsoft Defender for Endpoint, it allows rules by serial number, read-only and audit mode, and logs every access.

On Entra ID joined devices, recovery keys for removable sticks are not stored in Entra ID automatically the way the system disk's are. If sticks are encrypted from Intune-only devices, decide where the recovery password is recorded (or encrypt them from an AD-joined IT computer).

What you want to avoid is the same thing configured by GPO and by Intune at once on hybrid devices: two sources with different values are the first suspect for any odd behaviour.

5. The ticket: "my company encrypted USB won't let me save"

Maria, in Purchasing, has an approved stick that IT encrypted months ago. She unlocks it with her password and opens the files, but when saving: You need permission to perform this action. On her Accounting colleague's computer the same stick works.

  1. Is it unlocked and encrypted? manage-bde -status E: on Maria's computer: Protection On, Lock Status: Unlocked. The stick is fine.
  2. Which policies does her computer get? gpresult /h C:\Temp\gp.html and, under Removable Storage Access, Removable Disks: Deny write access = Enabled, won by the USB-Purchasing-Block GPO someone linked to the Purchasing OU. That policy overrides BitLocker: not even encrypted sticks can be written.

Fix: remove Deny write access from USB-Purchasing-Block (the company policy is already covered by BitLocker To Go), gpupdate /force, unplug and plug the stick back in.

If Deny_Write is not there, the other causes in order:

  • Different identification field: Identification Field shows another value (a stick encrypted at home or before CONTOSO was set) and the policy denies sticks from other organizations. On an IT computer, with the stick unlocked, manage-bde -SetIdentifier E: gives it the current field.
  • The stick is not unlocked: the user sees it but has not entered the password. It shows as Lock Status: Locked.
  • Defender device control: a read-only rule by serial number. It shows in the Defender portal, on the device timeline.

In the ticket: the blocking policy, the source GPO, the change made and the test of saving a file.
