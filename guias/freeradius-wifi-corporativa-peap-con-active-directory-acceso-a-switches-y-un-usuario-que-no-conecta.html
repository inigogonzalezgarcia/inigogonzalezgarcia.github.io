FreeRADIUS: WPA2/WPA3-Enterprise corporate Wi-Fi with Active Directory, admin access to switches and a user who cannot connect

FreeRADIUS 3.2 on Ubuntu: clients.conf for access points and switches, PEAP-MSCHAPv2 against Active Directory with Samba winbind and ntlm_auth, why EAP-TLS with certificates is better, switch admin login by AD group, debugging with freeradius -X, and the user who cannot get on the Wi-Fi.

Level 3 · FreeRADIUS: corporate Wi-Fi and network access · 9 min read · Updated 6 Nov 2026

Rather practise it?Solve the simulated ticket "The corporate Wi-Fi rejects the domain users" in SysAdmin Desks ↗

What you'll get

A RADIUS server on Linux that decides who joins the corporate Wi-Fi (WPA2 or WPA3-Enterprise) with their Active Directory username and password, only if they are in the authorised group, and which also controls who logs in as administrator on the switches. And, when someone cannot connect, reading in the debug output which step it stops at: the access point, the certificate, the password or the group.

Before you start

  • A dedicated Ubuntu Server 24.04, with the baseline from Ubuntu Server: users, SSH, firewall and updates. Ubuntu's package is FreeRADIUS 3.2; the configuration still lives in /etc/freeradius/3.0/ (the folder name did not change with the version).
  • Ports: 1812/UDP (authentication) and 1813/UDP (accounting), open only from the management networks of the access points and switches.
  • DNS pointing at the domain controllers, synchronised time and an account allowed to join computers to an OU.
  • A server certificate for radius.contoso.local issued by the internal CA (Server Authentication usage) with its key, and that CA's root certificate already deployed to the laptops.
  • Two AD groups: sg-wifi-corporativa (who joins the Wi-Fi) and sg-red-admins (who administers the switches).

To validate MSCHAPv2 passwords this server joins the domain with Samba winbind, not with SSSD as in the Linux with Active Directory guide. Do not mix the two on the same machine: a dedicated RADIUS server avoids the conflict.

1. Install FreeRADIUS and join the server with winbind

The essentials of /etc/samba/smb.conf ([global] section):

ntlm auth = mschapv2-and-ntlmv2-only is the line most often forgotten: since Samba 4.5 the default rejects MSCHAPv2 and every Wi-Fi authentication fails even with the right password.

Note down both SIDs: steps 3 and 5 use them to filter by group without fighting backslashes inside the FreeRADIUS configuration.

2. clients.conf: access points and switches

Every device that asks the RADIUS server is a client with its shared secret. In /etc/freeradius/3.0/clients.conf, per network or per device:

  • A long, different secret for each group of devices; if the switches' one leaks, it is no use against the access points.
  • require_message_authenticator = yes protects against BlastRADIUS (CVE-2024-3596). EAP always carries the attribute; for switches, turn it on if their firmware sends it (in 3.2.5 and later the default is auto).
  • The shortname labels the logs and, in step 5, separates the switch policy.

On the controller or the access points, the Contoso-Corp SSID in WPA2/WPA3-Enterprise (transition mode, or WPA3-Enterprise only if every client supports it, with PMF required) pointing at server 10.10.99.50, port 1812 and the same secret.

The inner-tunnel site already calls mschap in its authorize and authenticate sections: no need to touch it. Certificates go in /etc/freeradius/3.0/certs/, owned by freerad, with the key at mode 640.

radtest uses the localhost client that ships in clients.conf with the secret testing123. An Access-Accept here means winbind, ntlm_auth and the group all work; anything that fails later is on the access point, the certificate or the laptop.

On the laptops, the Wi-Fi profile is deployed by GPO or Intune with server validation: the root CA ticked and Connect to these servers = radius.contoso.local. Without it, the user accepts any certificate and a rogue access point collects their MSCHAPv2 response.

4. EAP-TLS: the better option

PEAP-MSCHAPv2 depends on the user's password and has two problems: MSCHAPv2 is weak if someone captures the exchange, and Credential Guard (on by default in Windows 11 22H2 and later, and in the security GPO) blocks single sign-on with MSCHAPv2: Windows stops using the session password and asks for credentials.

With EAP-TLS, each device presents its own certificate, with no passwords, and retiring a device means revoking its certificate. In FreeRADIUS all it takes is the tls { tls = tls-common } block inside eap and a ca_file that is the CA issuing to devices. How to hand out those certificates from Intune is in NDES and Cloud PKI. The usual path is a few weeks of coexistence: EAP-TLS for managed devices and PEAP for those without a certificate yet.

6. Debugging with freeradius -X

On Ubuntu the binary is called freeradius (on other distributions, radiusd -X). Stop the service and start it in the foreground, which shows each request step by step:

  • The line Ready to process requests says the configuration loads. If it does not appear, the syntax error is just above it, with file and line.
  • Each request carries a number in brackets, (7); find the user and follow that number down to Sent Access-Accept or Sent Access-Reject.
  • When done, Ctrl+C and sudo systemctl start freeradius. -X mode is not for leaving running.

7. The ticket: "I cannot connect to the corporate Wi-Fi"

Laura Prado, Accounts, Windows 11 laptop: "Contoso-Corp asks for my username and password and will not connect; my colleagues are fine". With freeradius -X running, you ask her to try again and search for laura.prado.

Nothing shows up. The request does not arrive or is dropped. If you see *Ignoring request to auth address * port 1812 bound to server default from unknown client 10.10.41.23*, that access point sits on a network clients.conf does not cover (a new AP on another subnet). If the client exists but the secret does not match, you will see invalid Message-Authenticator warnings. Fix it in clients.conf or on the controller.

It stops in the TLS tunnel.

The laptop does not trust the server certificate: the root CA is missing, the profile points at another CA, or the RADIUS certificate was renewed with a different chain. It is fixed in the Wi-Fi profile, not on the server.

It reaches MSCHAPv2 and fails.

The ntlm_auth message gives the cause: expired password, Wrong Password (the laptop has the old one saved; forget the network and reconnect), locked or disabled account. If the password is right but the user is not in sg-wifi-corporativa, the request also ends in Login incorrect: check with Get-ADPrincipalGroupMembership laura.prado | Select-Object Name. Remember winbind caches groups for a few minutes.

It asks for credentials every time and never saves them. That is Credential Guard with PEAP-MSCHAPv2 (step 4). The lasting fix is EAP-TLS for that device, not turning Credential Guard off.

If wbinfo -t fails, the problem affects everyone, not just Laura: the RADIUS server's computer account in AD has been deleted or reset; rejoin with net ads join.

In the ticket: time, access point, the debug line with the reason, the change made and proof she connects.

Next steps

  • NDES and Cloud PKI to move from PEAP to EAP-TLS with a certificate on each device.
  • The security GPO explains Credential Guard and why it breaks MSCHAPv2.
  • A second RADIUS server with the same configuration, added as secondary on the controller and the switches: if this one goes down, nobody gets on the Wi-Fi.
