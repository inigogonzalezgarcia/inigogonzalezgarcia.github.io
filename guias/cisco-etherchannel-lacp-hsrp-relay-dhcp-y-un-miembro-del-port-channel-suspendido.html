Cisco: EtherChannel with LACP between core and access, HSRP for the gateways, DHCP relay and a suspended port-channel member

Bundling an access switch's uplinks with LACP, aligning spanning tree with the gateway, HSRP (or VRRP) with priority, preempt and uplink tracking, ip helper-address to two DHCP servers, and a floor that drops now and then because of a flapping member and a suspended one.

Level 4 · Cisco switches and routers · 9 min read · Updated 6 Nov 2026

Rather practise it?Solve the simulated ticket "A port-channel member is suspended" in SysAdmin Desks ↗

What you'll get

Removing the single points of failure between a floor and the core: two cables per access switch working as one (EtherChannel with LACP), two core switches sharing each VLAN's gateway (HSRP), DHCP reaching the user VLANs through both of them (relay), and knowing how to read a port-channel when one of its members drops now and then or ends up suspended. The VLANs, trunks and the site router guide covers trunks and the egress route; this one carries on from there.

Before you start

  • Two core switches, CORE-01 and CORE-02 (Catalyst 9300 or 9500 with IOS XE 17.x), independent: if they are a stack or a StackWise Virtual pair, the gateway is already a single device and HSRP is not needed.
  • Access switches (SW-P2-01, Catalyst 9200) with four uplinks: two to each core.
  • VLAN 10 management (10.10.0.0/24), 20 users (10.20.0.0/24), 30 voice (10.30.0.0/24). DHCP on two Windows servers in failover, 10.10.0.10 and 10.10.0.11.
  • A change window, console access and reload in on every device you touch.

1. EtherChannel with LACP between access and core

A port-channel joins several physical links into one logical link: more bandwidth, and if a cable fails traffic carries on over the other without spanning tree recalculating. LACP is the protocol that negotiates the bundle and checks that the same device is on the other side.

On CORE-01, the same with its two ports towards the floor (channel-group 21 mode active and interface Port-channel21); on CORE-02, likewise with its own.

  • mode active on both ends: LACP talks and negotiates. Never mode on: it forms the bundle without asking, and a crossed cable or an unconfigured end ends up as a loop.
  • The trunk configuration goes on the Port-channel and the switch copies it to the members. All members must match on speed, duplex, mode, native VLAN and allowed VLANs; if one differs, it is suspended.
  • src-dst-ip spreads traffic by source and destination IP pair. A single conversation always uses the same cable: two 10 Gb links do not make a 20 Gb backup copy.

(SU) on the port-channel and (P) on each member is correct. show lacp neighbor tells you which device (System ID) and which port is on the other side of each member: the two in one bundle must show the same System ID.

2. Spanning tree aligned with the gateway

With two logical uplinks (Po1 and Po2), spanning tree blocks one per VLAN. The core that is root for a VLAN should also be its active gateway; otherwise traffic comes in through one core and crosses to the other over the link between them.

That way CORE-01 carries management and users, CORE-02 carries voice, and both uplinks do work.

3. HSRP for the user gateways

Devices have one gateway, 10.20.0.1. With HSRP that IP is virtual: the active core holds it, and if it fails, the other takes it over within seconds.

On CORE-02, Vlan20 with ip address 10.20.0.3, the same group, the same virtual IP and the same key, with the default priority (100) and preempt too. For VLAN 30, the other way round: CORE-02 with 110.

  • priority: the highest wins. preempt lets the preferred one take the role back when it returns; delay minimum 60 gives it a minute for its routes and spanning tree to settle before taking over from the other.
  • track: Te1/0/48 is CORE-01's link to the firewall. If it fails, the priority drops to 90, CORE-02 (100) becomes active and users go out through it. Without tracking, CORE-01 would stay the gateway with no way out.
  • HSRP version 2 uses the virtual MAC 0000.0c9f.fXXX (group in hex): in a PC's ARP table, the gateway shows 0000.0c9f.f014 for group 20.

VRRP does the same and is a standard: use it if the two cores come from different vendors. On IOS XE: fhrp version vrrp v3, and on the interface vrrp 20 address-family ipv4, address 10.20.0.1 primary, priority 110 and track 1 decrement 20. In VRRP preempt is on by default.

4. DHCP relay: ip helper-address on both SVIs

A DHCP request is a broadcast and does not cross the router. On each user VLAN interface, on both cores:

  • The core forwards the request as unicast to both servers and puts its own VLAN IP (10.20.0.2 or 10.20.0.3) in giaddr. The server picks the scope from that address: there must be a 10.20.0.0/24 scope with gateway 10.20.0.1 (the virtual one, never the physical).
  • With both cores relaying, the server receives two copies of each request. That is normal: it answers once.
  • By default ip helper-address also forwards TFTP, DNS, TACACS, NetBIOS and time. The no ip forward-protocol lines leave just DHCP.
  • If the access switches run DHCP snooping, they add option 82 with an empty giaddr and the core drops those requests. Either trust it on the relay (ip dhcp relay information trusted on the SVI) or remove it at the access layer (no ip dhcp snooping information option).

5. The ticket: "floor 2 drops for a few seconds several times a day"

Thursday, 11:20. Several users on floor 2 notice short drops: Teams freezes, a remote session reconnects. It is not the whole floor at once, nor always the same people.

Two different problems in the same picture. Each member's letter tells you where to look:

StateWhat it meansWhere to look
PIn the bundle and passing trafficNothing
DLink down; if it alternates with P, the member is flappingPhysical: optic, patch lead, error counters
sSuspended: its configuration does not match the bundle'sshow logging: the reason is in brackets
IStand-alone: receives no LACP from the other endThe other side has no channel-group, or the cable goes to another switch

Te1/1/2 goes down and up: every time it drops, the conversations using that cable are lost for a moment until they are redistributed. That is why it is not the whole floor.

CRC errors and a received power of -14.8 dBm against -2.9 on its partner: the problem is the fibre or the connector. Clean the connectors, replace the fibre patch lead in the rack and, if it persists, the optic (here and on CORE-01).

Te1/1/4 suspended: the log says vlan mask is different. show running-config interface Te1/1/4 shows switchport trunk allowed vlan 10,20 on the member: someone changed it directly during another incident and it no longer matches Po2. Put the member back in line with the others and keep the configuration on the port-channel only:

  • udld port aggressive (on both ends of each fibre) shuts down a link that transmits in one direction and not the other, instead of leaving it black for the minute and a half LACP takes to notice at its normal rate.
  • Trunk changes are made on the Port-channel, never on a single member.
  • If a member shows as I, check with show lacp neighbor and show cdp neighbors which switch it really reaches: a cable crossed between CORE-01 and CORE-02 is the classic case.

In the ticket: port-channel and members with their state before and after, counters and optical power, what was cleaned or replaced, the corrected configuration line and the result.
