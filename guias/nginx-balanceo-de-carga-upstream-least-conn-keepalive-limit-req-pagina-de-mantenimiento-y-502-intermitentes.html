Nginx as a load balancer: upstream with round robin, least_conn and ip_hash, passive health checks, keepalive, limit_req, a maintenance page and intermittent 502s

Spreading an application across several servers with an upstream block: round robin with weights, least_conn, ip_hash and hash, max_fails and fail_timeout, taking a node out with down, keepalive connections, limiting requests with limit_req, a log with the backend that answered, a maintenance page with an exception for IT, and the 502s and 504s that come and go.

Level 3 · Nginx and Apache · 9 min read · Updated 6 Nov 2026

What you'll get

Putting Nginx in front of two or three servers running the same application and making distribution, a node failing and maintenance things you control: which balancing method to use, when Nginx stops sending traffic to a failing node, how to take one out for patching, how to slow down whoever makes a thousand requests a minute to the login form, a maintenance page IT can bypass, and how to find the guilty node when "the intranet fails now and then".

Before you start

  • Nginx 1.24 or later (Ubuntu 24.04 or RHEL 9) already publishing the application with TLS, headers and timeouts as in the reverse proxy guide. This guide starts from that server and changes what sits behind proxy_pass.
  • Two or more application servers (here 10.20.30.11, .12 and .13, port 8080) with the same version deployed and, if the application keeps a session, a shared session store (database, Redis) or a balancing method with affinity.
  • A health URL in the application (/health) that returns 200 only if the application and its database respond.

  • ip_hash uses the first three octets of the IPv4 address: every user in 10.20.4.0/24 goes to the same node, and so does an office that leaves through a single NAT. If distribution looks very uneven, that is why.
  • A server marked backup only gets traffic if all the others are down. It cannot be used with ip_hash or hash.
  • zone keeps the nodes' state in shared memory: every worker process sees the same failure state instead of each having its own.

2. Passive health checks: max_fails and fail_timeout

Open source Nginx does not probe the backends on its own (active checks, health_check, are NGINX Plus). What it does is passive: it counts failures of real requests.

  • By default, max_fails=1 and fail_timeout=10s: a single failure takes the node out of rotation for 10 seconds; after that, Nginx sends it a real request as a test and, if it works, brings it back.
  • What counts as a "failure" is decided by proxy_next_upstream: by default error timeout, that is, failing to connect or a timeout expiring. A 500 or 502 returned by the application itself does not count as a failure unless you add http_500, http_502, http_503.
  • proxy_connect_timeout 3s: with the default (60 s), a powered-off node makes users wait a minute before moving on to the next one.
  • POST requests are not retried on another node once they have been sent, unless you add non_idempotent. Do not add it on order or payment forms: the order could be recorded twice.
  • To check health for real, monitoring queries /health on each node directly (not through Nginx), for example with one Zabbix web scenario per server.

Taking a node out for patching: mark it down, reload, and Nginx stops sending it new requests; those in progress finish.

3. Keepalive to the backends

Without keepalive, Nginx opens and closes a TCP connection to the backend on every request. With heavy traffic, that means thousands of connections in TIME_WAIT and added latency. Three pieces, all three needed:

  • keepalive 32; in the upstream: up to 32 idle connections kept per worker process.
  • proxy_http_version 1.1; in the location: HTTP/1.0 has no persistent connections.
  • proxy_set_header Connection ""; in the location: otherwise Nginx sends Connection: close and the backend closes.

And a fourth that prevents an intermittent error: the upstream's keepalive_timeout (60 s by default) must be lower than the time the backend keeps an idle connection open. If the backend closes first, Nginx sometimes reuses a connection the other side has just closed (you will see it in section 7).

4. Limiting requests with limit_req

limit_req slows down a client making too many requests: a badly written script, a bot trying passwords on /login. A zone is declared in http and applied wherever needed:

  • rate=10r/m on /login is 10 attempts per minute per IP; burst=5 nodelay lets a spike of 5 through at once with no waiting. Anything beyond that gets 429.
  • Without limit_req_status, a rejection is a 503, which gets confused with the maintenance page and with a backend that is down. Set 429.
  • An empty key is not counted: that is how monitoring and IT stay out of it.
  • If there is another load balancer or a WAF in front of Nginx, $binary_remote_addr is that device's IP and every user shares the limit. First set_real_ip_from 10.20.1.10; and real_ip_header X-Forwarded-For; to recover the real IP.
  • To start without risk, limit_req_dry_run on; for a week: it logs what it would have rejected and rejects nothing.

6. A maintenance page with an exception for IT

For an application upgrade: everyone sees a static page with a 503 and Retry-After, except the IT network, which gets in to test.

  • Turn it on with sudo touch /var/www/mantenimiento/ACTIVO and off with sudo rm. Nginx checks the file on every request: no reload needed.
  • The page, an index.html with the CSS inside it: any other file it requests (an image, a stylesheet) would also get the maintenance page.
  • The 503 with Retry-After tells search engines and monitors it is temporary.

7. The ticket: "the intranet fails now and then: 502s and, sometimes, it hangs and gives 504"

Wednesday, 10:15. Several departments say the same thing: the intranet works, but every so often a page gives 502 Bad Gateway and other times it hangs for a minute and ends in 504 Gateway Time-out. On reload, it works.

  1. One node or all of them? The step 5 log grouped by backend and status:

The 502s and 504s all come from node 13. The error log says why:

  1. Take the node out while you investigate: down and reload (step 2). The errors stop at once.
  2. The cause on the node: on srv-app-13, journalctl -u intranet --since "1 hour ago" shows the application process restarting from lack of memory every few minutes since yesterday's deployment; it only installed correctly on two of the three nodes. The application team is told and the node comes back when /health returns 200.
  3. Why users saw it: connections closed mid-response and read timeouts did not count towards taking the node out with the default configuration, and the POST is not retried. With max_fails=3 fail_timeout=30s, proxy_next_upstream error timeout http_502 http_503 and a sensible proxy_read_timeout, the node leaves rotation by itself after three failures.
