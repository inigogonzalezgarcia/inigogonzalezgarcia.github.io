Windows Defender Firewall by GPO: profiles, inbound rules by program, port and scope, no local rules, dropped-packet logging, management rules, and the application that stops working

Configuring the three firewall profiles from a GPO, creating inbound rules by program and by port limited to the networks that use them, turning off local rules, logging dropped packets to pfirewall.log, opening WinRM, Remote Desktop and ICMP only to the admin network, and finding what blocks an application with the log, netsh and Get-NetFirewallRule.

Level 2 · GPO: drives, printers and preferences · 7 min read · Updated 6 Nov 2026

What you'll get

The firewall on every computer and server governed from AD: on in all three profiles, with the inbound rules that are needed and only from where they are needed, without each installer opening ports on its own, with a log of what is dropped, and with the management rules (WinRM, Remote Desktop, ping) open to the admin network. And a method for when an application stops working the day the GPO applies.

Before you start

  • GPMC with RSAT and permissions to create and link GPOs on the computer and server OUs. The network drives and printers guide explains filtering and gpresult.
  • An inventory of what listens on each server: Get-NetTCPConnection -State Listen and each application's record. Without it, turning off local rules is a lottery.
  • The networks: workstations 10.20.0.0/16, servers 10.10.10.0/24, admin 10.10.50.0/24.
  • A pilot OU with a couple of computers and one server of each kind (file, application, print).

1. Profiles and baseline values

Windows applies a profile per network: Domain if the device authenticates against a domain controller through that interface, Private if someone marked it so, and Public for everything else. A laptop at home is on Public; the same laptop at the office, on Domain.

In Computer Configuration › Policies › Windows Settings › Security Settings › Windows Defender Firewall with Advanced Security, right-click the node › Properties, on each profile tab:

  • Apply local firewall rules = No is the key decision: from then on only GPO rules count. Whatever an installer or an admin creates locally is ignored. That is the goal, and also what breaks things (section 5).
  • The same on Private and Public. On Public, also no management exceptions: nobody manages a laptop on a hotel network.
  • The default log size, 4096 KB, fills in minutes on a busy server.

2. Inbound rules: program, port and scope

A good rule says what (program or port), from where (scope), on which profile, and has a name that still makes sense a year from now. Inbound Rules › New Rule:

  • By program: the executable path with variables (%ProgramFiles%\Contoso\Billing\BillSrv.exe). It keeps working if the service changes port, but breaks if an update changes the folder (paths with a version number).
  • By port: protocol and local port. For services running inside svchost.exe, which share an executable, it is the only sensible option.
  • Scope: Remote IP addresses with the network that uses the service. It is what reduces risk the most and what is least often filled in.
  • Profile: only Domain for almost everything server-side.

With Open-NetGPO changes are made in memory and Save-NetGPO writes them to SYSVOL in one go: faster, and no half-written GPO if the script fails.

One firewall GPO per role (FW-Computers, FW-Servers-Base, FW-Servers-App, FW-Servers-Print) instead of one with everything. Rules from several GPOs add up; profile values are decided by the GPO that wins on order.

4. Check on the device

  • DomainAuthenticated confirms the domain profile. If a domain server shows Public, no Domain-profile rule applies: it is a DNS or DC-reachability problem, not a firewall one.
  • LocalFirewallRules N/A (GPO-store only) confirms local rules are ignored.
  • -PolicyStore RSOP shows the rules coming from GPO; -PolicyStore PersistentStore, the local ones; -PolicyStore ActiveStore, what is really enforced.

5. The ticket: "since this morning the billing application won't connect"

Tuesday, 9:10. Accounting opens the billing client and gets Cannot connect to the server. Last night FW-Servers-Base (with Apply local firewall rules = No) was linked to the application servers OU.

  1. From a workstation: Test-NetConnection srv-app03 -Port 8443 returns TcpTestSucceeded : False, while ping and 3389 from the jump host work. The server is alive; something is closing that port.
  2. On the server, the log:
  1. Reading it: the service listens on 8443, SYNs from the workstations arrive and are dropped (DROP ... RECEIVE), and the rule that opened the port exists but is local (PersistentStore): the installer created it and the new GPO says local rules do not count.

Fix: the rule moves into the role's GPO, FW-Servers-App, with the right scope (the rule from section 2), gpupdate /force on the server and Test-NetConnection again from a workstation: True. Apply local firewall rules is not turned on for everyone because of one application.

If the log says nothing:

  • The file does not exist or does not grow: the firewall service (NT SERVICE\mpssvc) needs write permission if the log path is not the default one.
  • There is no DROP and the application still cannot connect: the problem is not the Windows firewall. Look at the network firewall between VLANs or the service itself.
  • Get-NetConnectionProfile says Public: the server does not recognise the domain network and applies another profile.

A ticket like this is not fixed by turning the server's firewall off "to test" and leaving it so. If you need to rule it out, a local Set-NetFirewallProfile -Profile Domain -Enabled False does not work with the GPO applied; test with a temporary GPO rule limited to the user's IP, confirm, and replace it with the final one.
