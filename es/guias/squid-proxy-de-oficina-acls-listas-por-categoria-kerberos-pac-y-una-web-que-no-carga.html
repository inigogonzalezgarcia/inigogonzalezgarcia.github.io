Squid: proxy de oficina con ACLs, listas por categoría, Kerberos con Active Directory, PAC y una web de proveedor que no carga

Squid 6 en Ubuntu como proxy de la oficina: el puerto, las ACL y por qué el orden lo decide todo, bloqueos por categoría desde ficheros, autenticación Kerberos con Active Directory y grupos, por qué casi nunca compensa el SSL bump, el PAC y WPAD, cómo leer access.log y la web de un proveedor que no carga a través del proxy.

Nivel 3 · Squid: proxy web de la oficina · 10 min · Actualizado 6 nov 2026

Qué vas a conseguir

Un proxy web para la oficina que sabe quién navega (con su usuario de Active Directory y sin pedir contraseña), aplica reglas distintas según el grupo, bloquea categorías desde listas que se mantienen en ficheros y deja un registro legible de cada conexión. Y, cuando una web "no carga por el proxy", encontrar en una línea de access.log si es una regla, un puerto, la autenticación o la salida a Internet.

Antes de empezar

  • Un Ubuntu Server 24.04 con la base de la guía Ubuntu Server: usuarios, SSH, firewall y actualizaciones. El paquete squid de Ubuntu 24.04 es la versión 6.
  • Un nombre en DNS, proxy.contoso.local, apuntando al servidor (10.10.99.40). Kerberos lo necesita: con la IP no funciona.
  • Hora sincronizada con los controladores de dominio y una cuenta de servicio en AD, svc-squid, sin caducidad de contraseña.
  • En el firewall perimetral, salida a 80 y 443 solo desde el proxy (si los puestos también salen directos, el proxy es opcional y nadie lo nota).

1. Instalar y dónde va la configuración

El squid.conf de Ubuntu es largo y comentado; lo tuyo va en un fichero aparte, /etc/squid/conf.d/contoso.conf, que se carga en el punto del include: después de las reglas de seguridad de puertos y antes del deny all final. El puerto por defecto, 3128, ya está definido; no lo repitas en tu fichero o Squid intentará abrirlo dos veces.

Dos comandos para cada cambio:

-k parse revisa la sintaxis sin tocar el servicio; -k reconfigure recarga sin cortar las conexiones abiertas.

2. ACLs: el orden lo decide todo

Una ACL es una condición con nombre (origen, destino, puerto, usuario, grupo). Las reglas http_access se evalúan de arriba abajo y gana la primera cuyas condiciones se cumplen todas (las condiciones de una misma línea se combinan con Y). Si ninguna coincide, se aplica lo contrario de la última, por eso todo acaba en http_access deny all.

Las consecuencias prácticas:

  • Las excepciones van antes que los bloqueos. Una lista de permitidos debajo de un deny no se llega a leer.
  • Lo que no debe pedir autenticación (actualizaciones de Windows, el antivirus, servicios que no saben autenticarse) va antes de la regla que exige usuario.
  • http_access deny !autenticado es la forma habitual de forzar la autenticación: al no cumplirse, Squid responde 407 y el navegador se autentica.

La variable KRB5_KTNAME la usa el helper de grupos; el de autenticación recibe el keytab con -k. Al principio de contoso.conf:

  • -r quita el reino del nombre: en el log aparece laura.prado, no laura.prado@CONTOSO.LOCAL.
  • El helper de grupos consulta AD por LDAP con la identidad del keytab y guarda la respuesta una hora (ttl=3600): un usuario añadido al grupo tarda hasta una hora en notarlo, o hasta un squid -k reconfigure.
  • NTLM como respaldo (equipos fuera del dominio) exige unir el proxy con Samba winbind y negotiate_wrapper_auth. Si todos los puestos están en el dominio, mejor no: es otra pieza que mantener.

Kerberos solo funciona si el navegador llega al proxy por nombre. Si el PAC o la GPO dicen 10.10.99.40:3128, el navegador no encuentra ticket para esa IP, intenta NTLM y, sin NTLM configurado, el usuario ve una ventana de credenciales que no acepta ninguna.

5. SSL bump: por qué casi nunca

SSL bump descifra el HTTPS en el proxy: Squid crea al vuelo un certificado para cada web firmado por una CA interna que todos los equipos deben tener en confianza. Permite ver URLs completas y analizar contenido, pero:

  • Rompe las aplicaciones con certificado fijado (pinning): clientes de banca, actualizadores, algunas aplicaciones de escritorio y de móvil. Cada una acaba en la lista de excepciones.
  • La CA interna se convierte en una pieza crítica: quien tenga su clave puede suplantar cualquier web ante cualquier equipo.
  • Descifrar banca, salud o correo personal de los empleados tiene implicaciones legales y de privacidad que se deciden con RR. HH. y el DPD, no en una configuración.
  • Necesita el paquete squid-openssl y más CPU.

Para bloquear por dominio no hace falta: con proxy explícito el nombre ya viaja en el CONNECT. Si el requisito es inspección de contenido, suele resolverse mejor en el firewall perimetral o en un servicio de seguridad web dedicado.

6. Repartir la configuración: PAC y WPAD

Un PAC es un pequeño JavaScript que el navegador consulta para cada URL y que decide proxy o salida directa:

  • Se sirve por HTTP desde cualquier servidor web interno con tipo MIME application/x-ns-proxy-autoconfig.
  • Se distribuye con la URL del script: por GPO (preferencias de Configuración de Internet), por la directiva de Edge ProxyPacUrl o en Intune desde el catálogo de configuración. Edge y Chrome usan la configuración del sistema si no tienen la suya.
  • WPAD es el descubrimiento automático (http://wpad.contoso.local/wpad.dat). Funciona, pero el servidor DNS de Windows bloquea el nombre wpad por defecto (lista global de bloqueo de consultas) y abrirlo permite que un equipo malicioso se anuncie como proxy. Una URL explícita por directiva es más predecible.
  • "PROXY proxy.contoso.local:3128; DIRECT" deja salir directo si el proxy cae. Solo tiene sentido si el firewall permite la salida directa; si no, el usuario solo gana un error distinto.

7. Leer access.log

/var/log/squid/access.log, una línea por petición. Las horas vienen en segundos desde 1970; para leerlas:

Columnas: hora, milisegundos, IP del cliente, resultado/código, bytes, método, destino, usuario, cómo salió y tipo.

8. El ticket: "la web del proveedor no carga por el proxy"

Compras no puede entrar en el portal de un proveedor, https://portal.fabrikam.com:8443. Edge muestra ERR_TUNNEL_CONNECTION_FAILED; desde un móvil con datos, carga. Ese error es del navegador cuando el proxy contesta al CONNECT con algo distinto de 200: la respuesta está en el log.

Un 403 con el usuario identificado: no es la autenticación, es una regla. Por orden:

  1. ¿Está en una lista? grep -rn fabrikam /etc/squid/listas/ no devuelve nada.
  2. ¿El puerto? Las primeras reglas de squid.conf deniegan CONNECT a puertos que no estén en SSL_ports, y en Ubuntu esa ACL solo tiene el 443. Ese es el 403.
  3. La corrección, en /etc/squid/squid.conf junto a la línea acl SSL_ports port 443: acl SSL_ports port 8443. Si prefieres no abrir 8443 a cualquier destino, una ACL dstdomain para el proveedor y una regla http_access allow CONNECT combinada, situada antes del deny CONNECT !SSL_ports.
  4. sudo squid -k parse && sudo squid -k reconfigure y otra prueba:
  1. Ahora un 503 tras 30 segundos: la regla deja pasar, pero el proxy no consigue conectar. El firewall perimetral solo permite al proxy salir a 80 y 443. Se pide la regla de salida al 8443 hacia la IP del proveedor (con su ticket) y la prueba devuelve 200.

Otros finales del mismo síntoma: TCP_DENIED/407 en bucle con usuario - (una aplicación que no sabe autenticarse: su dominio a sin-autenticacion.txt); un 403 por una lista que incluye el CDN del proveedor (excepción documentada); un 503 inmediato por DNS (el proxy resuelve con sus propios servidores DNS: dig portal.fabrikam.com desde el proxy).

En el ticket: línea del log antes y después, regla o ACL cambiada, cambio en el firewall si lo hubo y la prueba final.
